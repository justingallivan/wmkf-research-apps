# Compact ROR index measurement — ROR v2.11

**Measured:** 2026-08-07  
**Release:** ROR v2.11, schema 2.1, published 2026-08-03  
**Version DOI:** [10.5281/zenodo.21773148](https://doi.org/10.5281/zenodo.21773148)  
**Runtime:** Node v26.6.0, Apple M3 arm64, 16 GiB RAM, macOS  
**Authority:** measurement only; no runtime resolver, benchmark judge, case, or
production setting changed

## Result

[VERIFIED via the pinned v2.11 source and two deterministic builds] The full
retrieval-only index is 80,423,454 bytes uncompressed, 29,432,170 bytes with
gzip, and 24,657,009 bytes with Brotli quality 6. It contains all 135,710 ROR
records plus exact-name, domain, token, and character-trigram postings.

[VERIFIED via fresh-process probes] Relative to the raw JSON, the plain compact
JSON is 73.6% smaller and takes 52.7% less time to read and parse in this run.
Its immediate post-parse process RSS, while the input buffer is still retained,
is 36.5% lower. After releasing buffers and forcing GC, process RSS is only 6.7%
lower and parsed-object heap is 3.1% larger because the retrieval postings create
many small arrays and numbers. RSS is process residency, not a direct live-object
measure; it need not fall when ArrayBuffers are released.

[VERIFIED via applying the same codecs to both JSON artifacts] Compression
reverses the byte-size advantage: the full index is 35.4% larger than the raw
JSON under gzip and 84.2% larger under Brotli. The official 35,648,847-byte ZIP
is not the apples-to-apples comparator because it contains both JSON and CSV.

[INFERENCE from the measured process-memory and compression tradeoff] This
JSON representation is useful for offline benchmarking, but it is not yet
justified as a request-path static asset. A production substrate would need a
separate decision about split/lazy loading, a denser binary posting format, or
a warm batch service. No production-substrate choice is made here.

## Fresh-process load measurements

These are one-machine measurements, not latency promises. The operating-system
disk cache was not flushed. `Immediate RSS` is sampled directly after parse while
the input/decompression buffers remain referenced. The probe then releases
those buffers, forces GC twice, verifies that ArrayBuffer bytes fall to about
0.14 MB, and samples process RSS and heap again. Post-release RSS is still not
live-object memory because the allocator can retain resident pages. `Max RSS`
captures transient peaks that either point sample can miss.

| Artifact loaded | Total read/decode/parse | Immediate RSS | Post-release RSS | Post-release heap | Max RSS |
|---|---:|---:|---:|---:|---:|
| Raw JSON | 678.5 ms | 957,857,792 bytes | 655,458,304 bytes | 251,150,000 bytes | 937,392 KiB |
| Raw gzip | 770.1 ms | 1,254,703,104 bytes | 951,435,264 bytes | 250,265,768 bytes | 1,225,568 KiB |
| Raw Brotli | 782.2 ms | 1,252,311,040 bytes | 948,977,664 bytes | 250,270,496 bytes | 1,224,112 KiB |

| Index gzip | 426.2 ms | 721,207,296 bytes | 726,089,728 bytes | 258,936,928 bytes | 709,328 KiB |

The final end-to-end build process peaked at 1,519,344 KiB RSS. The measured
index build itself took 4.87 seconds; serialization took 0.34 seconds, gzip 2.92
seconds, and Brotli 1.62 seconds in that run.

## Scope and next decision

Generated source and index artifacts remain untracked under an ignored working
directory. The tracked files are only the release manifest, reproducible
builder/probes, tests, instructions, and this measurement.

This closes the roadmap's compact-index sizing question without approving a
production asset. The next safe institution-resolution work is to use the
pinned release strictly as an offline benchmark substrate, add canonical
expected ROR ids to a deliberately versioned benchmark revision, and make pair
evaluation relationship-aware. The frozen comparator inputs and prior results
must remain unchanged unless that versioned reset is explicitly undertaken.
