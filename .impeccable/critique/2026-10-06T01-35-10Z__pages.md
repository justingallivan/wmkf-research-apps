# Assessment A — App-wide staff UX critique (Operate mode)

Evidence: all 56 desktop screenshots, plus source. I could not capture mobile, so responsive findings come from reading the code. Nothing I found is P0: every task can still be finished. The pain comes from structure and accumulated additions, not from anything blocking.

## Corrections to orchestrator notes
- The nav has **17** links in this superuser session (rows of 6, 5 and 6), not 19. The count depends on each user's grants.
- Emoji heroes are **inconsistent**, not universal. Workbench (🗂️), Grant Reporting (📊) and Dynamics Explorer (💬) have emoji. Meeting Tracker, Review Panel, Integrity Screener, Scheduled Emails, Profile Settings and Admin have none. Cycle Dossier uses an SVG icon.
- `/meeting-tracker/visits` redirects to `/meeting-tracker` (the cycle schedule), not to home (`pages/meeting-tracker/visits/index.js`).
- The visit H1 is meant to show the request number: `SiteVisitEditor.js:235` appends `· #N` when `requestNumber` resolves. In production it showed a bare "Site visit", so the number did not resolve there.

## Design-specificity verdict
The parts are partly specific to the domain; the composition is generic. Good domain touches: reviewer-coverage bars on the request list, the Final Writeup "with leadership" state card, and Status tab copy ("Staff recommend; the board decides…"). The page skeleton, though, could belong to any Tailwind admin template: a centered marketing hero, an emoji link wall, then a column of same-weight white cards. Nothing in the layout reflects that a grant request moves through stages; the 11 request tabs are a flat strip with no stage or status cues.

## Cognitive load
Checklist failures, 6 of 8 (high load): single focus, chunking, visual hierarchy, one-thing-at-a-time, minimal choices, progressive disclosure. Grouping passes. Working memory partly fails, because stage has to be recalled across tabs.

Decision points with more than 4 visible options:
- Global nav: 17 links, flat, emoji-prefixed.
- Request page tabs: 11 (`pages/workbench/[requestId].js:50-62`).
- Reviewers sub-strip: 3 tabs plus 3 links = 6 targets, on top of the 11 main tabs.
- Meeting Tracker: 10 status chips, five of them showing (0). Also a row of 7+ session-date pills that overflows to the right, plus program, cycle and scope controls.
- Visit page attendees: 10 organizer chips, 10 staff + 9 board required chips, and the same 19 repeated for Optional. That is about 48 toggles before the Save button.
- Recording & Transcript card: about 10 actions (Open, Replace, Download TXT, Download VTT, Edit speaker names, Summarize, Upload a transcript, Generate from audio, Copy link, Issue new link).
- Admin tabs: 7.
- Home filter: 5 (acceptable).

Signs of accumulated additions in the code: `RecordingAndTranscriptCard.js` is 2,406 lines and `PostPresentationMaterialsCard.js` is 1,023. I have only file sizes for these, not a review of their internals.

## Emotional journey
- **Entry valley:** home has no nav. Every app page then opens with a 3-row emoji wall and a marketing-style centered hero. It reads as a hobby suite, not a calm workbench.
- **Mid peaks:** request Overview (clean snapshot plus summary cards), the Track Reviewers table, and the Final Writeup state card. Each shows one status and one action.
- **Deep valleys:** the Site Visit page and the Staff Deliberations tab. A completed visit opens as an empty-looking edit form, then a chip wall, then materials, then a recording card whose actions are still offered after the work is done (a disabled "Summarize presentation" under "Published Oct 5"). Staff Deliberations announces "Moved to Final Writeup" in success green, then keeps going with five filename rows and the full summary text.
- **End:** every page ends on "Written by… Built with Claude AI… Powered by Next.js…", which is the opposite of a reassuring close at the moments that matter most.

## Strengths
1. **Request list cards with coverage bars** (shot 3): a dense, meaningful reviewer signal (accepted / released / declined) right in the row.
2. **Cycle Dossier** (shot 58) and **Admin overview** (shots 46-47) are the best-structured pages. Dossier has a breadcrumb context bar, a 3-step stepper and a composition side rail. Admin has a left-aligned H1, tabs, a "Needs attention" block first, then destinations. Use them as the archetype models.
3. **Single-status cards done right:** the Final Writeup "with leadership" card (shot 20) and the Status tab (shot 21). Each shows one state, one sentence of meaning and one action. Copy is generally plain and honest about AI.

## Findings by surface (ranked within each)

### Global shell / nav
- **P1 — Flat 17-link emoji nav, about 160px tall, no current-app marker.** *Why:* Every page spends its first fold on navigation, and you can't tell where you are. The 17 targets mix daily tools (Workbench, Meeting Tracker) with rarely used utilities (Bulk Export, Expense Reporter). *Fix:* One row: Workbench · Meeting Tracker · Tools ▾ (grouped by phase like the home page) · Guide · Admin, with the current item marked by ink text and an underline. Drop the emoji or keep them only inside the menu. (`Layout.js:79-96`, `appRegistry.js`)
- **P1 — Interpolated `max-w-${maxWidth}` is dropped by Tailwind.** `Layout.js:75,271,278` builds the class with a template literal, and Tailwind only generates classes it finds written out as literals. `max-w-6xl` appears nowhere as a literal, so Scheduled Emails (`scheduled-emails.js:256`) gets no max-width at all: full-bleed nav and content (shot 51). Profile's `4xl` survives only because the literal exists in `pages/external/presentation/[token].js`. That narrow container then wraps the nav to 5 rows (shot 52). *Fix:* Replace the interpolation with a literal class map keyed by page archetype, and let the nav always use the shell width.
- **P1 — One surface, three names.** The nav says "Reviewers" (`appRegistry.js:52-53`), the hero says "Request Workbench", and the request back link says "Back to dashboard" (`[requestId].js:191`). *Fix:* Call it "Workbench" everywhere and make the back link "← Workbench · December 2026 Research".
- **P2 — Home has no nav or shell while every other page does.** *Fix:* Home uses the shell. Its tile grid becomes the "Tools" index, or Home becomes "My work" (assigned requests, upcoming sessions).
- **P2 — Vanity footer on operational pages.** *Fix:* Remove it, or reduce it to one muted line with the Guide link.
- **P2 — Mobile (code only):** `hidden md:flex` desktop nav plus a hamburger menu (`Layout.js:184-250`). The request tab strip scrolls horizontally (`overflow-x-auto min-w-max`). I did not verify whether the visit page's Staff/Board two-column chip grid collapses at narrow widths.

### Workbench list + views
- **P1 — Every view opens with a centered hero (emoji, H1, tagline) and the program/cycle selects, about 450px before content.** It repeats on all 5 views. *Fix:* Use a list/queue header: a left-aligned H1 of about 1.5rem with the program and cycle selects inline on the same row, and the views as underline tabs directly beneath. Remove `PageHeader` from WorkbenchShell (`WorkbenchShell.js:183-188`).
- **P1 — The request list is a stack of ~165px cards, so only about 3.5 requests fit per screen.** *Why:* Triaging a cycle means scanning dozens of requests. *Fix:* A dense table or row list: #, institution/PI, coverage bar, triage, next action, about 56px per row. Keep the coverage bar.
- **P2 — Rows are `div role=button` with `router.push`** (`RequestListPanel.js:328-336`), so there is no middle-click and no new tab. *Fix:* Render each row as a `Link` and keep the triage select's `stop()`.
- **P2 — The triage `<select>` sits inline in the row as a 4px-radius mini control**, so a state change can happen from a scanning view. *Fix:* Keep it, but style it as a status chip with a menu, consistent with chips elsewhere.
- **P2 — "Find and open a request" is collapsed**, even though opening a request is the most common action. *Fix:* A search box always visible in the header row.
- **P3 — Odd placement of the "Not filtered by program" / "Research programs only" hint under the program select** (shots 44-45). *Fix:* Show scope once, as text in the header.

### Request page
- **P1 — 11 flat tabs with no stage or status cues.** *Why:* You can't see where the request is without clicking through. *Fix:* Group the tabs in lifecycle order (Proposal · Review · Deliberation · Decision · Award) or add per-tab status dots or counts. Make Overview a "next step" summary. The current Overview has no next-action line.
- **P1 — The error state wipes request identity** (shot 14). *Fix:* Keep the header from context or route params, show errors inside the affected tab, and add a Retry button. Never show raw "Failed to fetch".
- **P1 — The Staff Deliberations tab after handoff:** a green "Moved to Final Writeup" box (success color used for a redirect), then five filename rows with UUIDs, then the full presentation summary inline. *Fix:* A read-only summary with one ink link, "Continue in Final Writeup →". Materials go in a compact list without filenames; the summary collapses to its first paragraph with "Read full summary".
- **P1 — The Awardee tab breaks the system** (`AwardeeTab.js:951,1328` use `bg-blue-700`; `:1035,1201` use `bg-green-700`; `rounded`, raw `<button>`). It has no card, a nested sub-tab strip, and a full-width email input. *Fix:* Use the shared `Button` and the ink primary, wrap sections in the standard card, and use a single status header.
- **P2 — The Reviewers sub-strip mixes tabs with settings links** (Campaign settings, Email templates, Manage in Profile). The "Track Reviewers 3" badge disagrees with "2 reviewers" in the body. *Fix:* Settings go behind one ⚙ menu, and the badge count means the same thing as the body count.
- **P2 — Link colors drift:** indigo text links on Overview, blue underlined links on Staff Deliberations and the visit page, and a blue filename link on Initial Assessment. *Fix:* Use one link style.
- **P2 — The Initial Assessment tab exposes storage plumbing** (`Artifacts/Initial Assessment/`, `a6b2ef92…docx`). *Fix:* Say "Initial Assessment draft (Word)" and keep the path in a details tooltip.

### Meeting Tracker home / visit / session
- **P1 — Completed visits and sessions open in edit mode** (`SiteVisitEditor.js:232-338`: the form renders first, then Materials and Recording at 337-338. `SessionEditor.js:455-520` does the same). *Fix:* Read-only summary header (date, format, link, attendees as a name list, status chip) with an Edit button. The form appears only on Edit or when scheduling a new visit.
- **P1 — The visit page has no request identity in production** (bare "Site visit" H1; the request number appears only inside the Subject field). Its subtitle reads like developer notes ("feeds the Staff Deliberations rail…"). *Fix:* Breadcrumb "Meeting Tracker › #1003222 The Secret History of Our Sun", H1 "Site visit", and a status chip.
- **P1 — About 48 attendee chips**, with the Optional set duplicating the Required set. *Fix:* A single people picker (typeahead plus a selected list) with a required/optional toggle on each selected person. Show no-email board members only on search.
- **P1 — The Recording & Transcript card offers about 10 actions** whether or not the steps are done. *Fix:* Show it as a stepper (Recording ✓ → Transcript ✓ → Summary ✓ → Board link). Done steps collapse to one line plus a "…" menu with Replace, Download and Regenerate. Only the next incomplete step gets a primary button.
- **P2 — Meeting Tracker home: 10 status chips (five at zero) plus overflowing date pills.** *Fix:* Hide zero-count chips, or put them behind "More". Make the dates a single select or a mini calendar. Rows carry full Zoom URLs with passwords. *Fix:* Show "Zoom ↗" instead.
- **P2 — "Open session" vs "Edit visit"**: the button labels for the two records aren't parallel. *Fix:* "Session" / "Visit", both opening the read view.
- **P3 — Duplicate "Back to the cycle schedule"** links at the top and in the form footer.

### Admin
- **P3 — Admin overview is already a good model.** Minor: the "Needs attention" alert duplicates the nav's red badge. Keep this page as the settings/admin archetype.

### Focused tools
- **P2 — Header styles disagree across tools:** Integrity Screener (no emoji, a `?`, content narrowed to about 1024px), Grant Reporting (emoji, two-line tagline), Review Panel (tagline "Phase A foundation (narrative-only…Claude chair)", content about 990px), Dynamics Explorer (emoji hero plus a separate superuser card plus another 💬 welcome block). *Fix:* Use a workspace/tool header: left-aligned H1, a one-line purpose, a `?` help link, and full shell width.
- **P2 — Product-internal language in taglines and home cards** ("Phase A", "D26", "Claude + OpenAI", "blind and separate from the D26 Cycle Dossier"). *Fix:* Write taglines in staff task terms.
- **P3 — Scheduled Emails shows a centered "Loading…" inside full-bleed layout.** *Fix:* Use a skeleton rows pattern.

## Top 5 app-wide priorities
1. **Shell and nav rebuild (P1):** a one-row grouped nav with a current marker; a literal width class per archetype (fixes the Tailwind purge); "Workbench" as the one name; home brought into the shell.
2. **Retire the centered `PageHeader` hero on operational pages (P1):** replace it with archetype headers (breadcrumb, left H1, status chip, primary action at right). This alone recovers about 300-450px per page.
3. **Read-first records (P1):** completed visits, sessions and handed-off tabs render as summaries. Editing is explicit.
4. **Cap the card stack and collapse finished steps (P1):** the visit page, Staff Deliberations and the Recording card become steppers or summaries with progressive disclosure.
5. **One button, link and tab vocabulary (P1/P2):** the shared `Button` only (11 raw colored `<button>`s vs 37 files that import the shared Button); one tab style per level; one link style; status shown once as a chip in the header.

## Proposed page-structure rules for DESIGN.md
**Archetypes.** Every page declares one archetype: Queue/List, Record Detail, Workspace/Tool, or Settings/Admin. Archetype sets width, header and section order.

1. **Width.** The shell uses `max-w-7xl` on every page, nav included. Settings/Admin and reading pages may narrow only their main column to `max-w-4xl`. Width classes are literals from a map; no interpolated `max-w-*`. *Broken by:* shots 51, 52, 55, 59.
2. **Header (all archetypes).** Left-aligned, in this order: breadcrumb or back link (one line, muted), H1 at 1.5rem/600 at most, one metadata line, and status chip(s) inline with the H1. The primary action sits right-aligned on the H1 row. Centered heroes, emoji in H1 and multi-line taglines are forbidden outside the home page. *Broken by:* shots 2, 23, 52, 55, 57, 59.
3. **Queue/List.** The header row holds the filters (program, cycle, scope) and search. Content starts within 240px of the top of the main area. Rows are dense (about 64px or less), each row is a real `<a>`/`Link`, and each row shows a next-action cue. *Broken by:* shots 2-3; `RequestListPanel.js:328`.
4. **Record Detail.** The record's identity (number, title, program/cycle) is always visible in the header, including in error and loading states. The record opens read-only, editing happens behind an explicit Edit control, and a completed or closed record never opens as a form. *Broken by:* shots 14, 26, 42.
5. **Section order.** Status and next action first, then the primary content, then supporting evidence, then history, audit and technical detail (collapsed). *Broken by:* the Staff Deliberations tab.
6. **Card stacking limit.** No more than 4 top-level cards before the first fold break. Beyond that, use tabs, a stepper, or collapsible sections. A card holds one topic and no more than one primary action.
7. **Progressive disclosure of finished work.** A completed step collapses to one line: label, ✓ state, timestamp and a "…" menu. Re-run, replace and regenerate live in that menu, never as visible buttons next to "Published". *Broken by:* shots 35-37.
8. **Multi-step flows** (visit materials, transcript, dossier, grant reporting) use the Cycle Dossier stepper pattern, with only the next incomplete step expanded.
9. **Status display.** A record's status appears once, as a chip in the header, using the DESIGN.md chip semantics. Green means confirmed success only; a redirect or "moved" notice is neutral or blue informational. *Broken by:* shot 17.
10. **Buttons.** No more than one ink primary per viewport region. All buttons come from the shared `Button` (primary, secondary, outline, danger); raw colored `<button>`s are lint-blocked. Text links are reserved for navigation. *Broken by:* `AwardeeTab.js:951,1035,1201,1328`.
11. **Tabs.** Level 1 (page sections) uses underline tabs. Level 2 (inside a section) uses a segmented control. Filters are chips. Use no more than 7 tabs per level, grouped or ordered by lifecycle, and each tab may carry a status dot or count. *Broken by:* the three tab styles; 11 request tabs.
12. **Filters.** Hide or disable chips with a zero count. More than 6 filter values collapse into a select or a "More" menu.
13. **People selection.** More than 8 selectable people uses a typeahead picker with a selected list, not a chip wall. Never render the same list twice.
14. **Empty, loading and error states.** Empty states say what's missing and offer the action that fills it. Loading uses skeletons in place, not centered text. Errors appear in the affected region with a plain-language message and Retry, and never replace the page identity. Raw exception strings are forbidden.
15. **Internal identifiers.** Staff UI never shows UUIDs, raw tokens, storage paths or full meeting-URL query strings. Show human labels with a copy or open affordance instead.
16. **Nav model.** At most 7 top-level items in one row: Workbench, Meeting Tracker, Tools ▾, Guide, Admin, and the user menu. The current item is marked. Every authenticated page, home included, uses the same shell.
17. **Footer.** Operational pages carry no attribution footer.

## Persona red flags
**PD triaging a cycle ("Alex", power user)**
- About 610px of nav plus hero on every Workbench view; about 3.5 requests per screen.
- Rows can't be opened in new tabs (`div role=button`), and there's no bulk triage.
- To see where each request stands, Alex must open 11 tabs per request; the list doesn't show the next action per stage.
