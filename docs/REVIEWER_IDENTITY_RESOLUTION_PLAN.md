# Reviewer Identity Resolution — redesign plan

**Status:** Design proposal (no code yet). Authored by Codex (S213, 2026-06-02) at the user's request after a persistent false-match problem in Reviewer Finder.

**Trigger:** Searching "Li-Huei Tsai" (MIT PI) attached the Google Scholar profile of **Masayuki Nakano** — a postdoc *in her lab* (his Scholar affiliation reads "Li-Huei Tsai Lab, Picower Institute, MIT"). The institution-mismatch guard passed (he's genuinely at MIT), and there's no name-identity check, so his h-index/citations landed on her record. This "different person, same institution/lab" failure is recurrent.

**Verified at the code level (independently, before this plan):** `DiscoveryService.checkInstitutionMismatch` only compares institution, so a same-institution lab member passes; `SerpContactService.findScholarProfileViaGoogle` takes the first Scholar result without a displayed-name guard; metrics attach in `ContactEnrichmentService._attachScholarMetrics`.

**Recommended sequencing (added by Claude):** ship **Phase 1** (strict Scholar displayed-name guard + don't persist metrics without an identity-confidence status) as a standalone fast safety fix — it kills the live class without a rewrite and supersedes the insufficient S211 institution-aware attempt. Treat **Phase 2** (the shared identity resolver) as its own project. **Data-governance tie-in:** the S213 appresearcher collapse just migrated bibliometrics onto the person; some are wrong matches (Tsai's were cleared manually). When Phase 1 lands, audit the already-persisted Scholar/ORCID metrics rather than trusting them.

---

## 1. Root cause diagnosis

The current pipeline treats "candidate relevance" and "human identity" as the same problem. In `pages/api/reviewer-finder/analyze.js`, `handler` delegates candidate naming to `ClaudeReviewerService.analyzeProposal`, then `/discover` accepts those names as reviewer suggestions. That is fine for ideation, but it is not an identity anchor. The output is a human-readable suggestion, not a resolved person record with ORCID iD, Scholar author ID, institutional email, or a verified publication cluster.

The main false-match point is `DiscoveryService.verifyClaudeSuggestions` in `lib/services/discovery-service.js`. It searches PubMed by name variants via `buildAuthorQuery` and `buildDisambiguatedAuthorQuery`, filters articles with `filterToMatchingAuthorMultiVariant`, then accepts a candidate if enough papers remain. This verifies that someone with a compatible author name has relevant papers. It does not prove that the later ORCID or Scholar profile belongs to that same human. Its `verificationConfidence` is calculated by `calculateExpertiseMatch`, which is an expertise/publication topicality score, not an identity-confidence score.

`DiscoveryService.checkInstitutionMismatch` is specifically insufficient for the Tsai/Nakano failure. It asks whether the found affiliation conflicts with the suggested institution. In the reported case, Masayuki Nakano's Scholar snippet genuinely contains MIT and Li-Huei Tsai Lab, so institution mismatch does not trigger. This function can catch "same name, different institution," but it cannot catch "different person, same institution/lab." That is the precise failure mode.

The Scholar enrichment path compounds this. `ContactEnrichmentService._attachScholarMetrics` calls `SerpContactService.findScholarProfile`, then persists `googleScholarId`, URL, h-index, i10, and citations if `institutionMismatch` is false. `SerpContactService.findScholarProfileViaGoogle` searches Google for `"Name" institution site:scholar.google.com`, takes the first citations URL, extracts `user=...`, and returns `scholarName` from the result title and `scholarAffiliation` from the snippet. It does not perform a hard name-identity check between the target candidate name and the displayed Scholar profile name before `fetchScholarMetrics` is called.

ORCID has the same architectural issue, though the consequences are usually lower because ORCID is an explicit person identifier. `ORCIDService.findContact` calls `searchByName`, optionally narrows by affiliation, then uses either the first result with email or the top result. It does not score all ORCID candidates against name variants, affiliation history, works, DOI overlap, and external URLs before selecting one. So ORCID is used as an enrichment tier, not as a disambiguation authority.

Deduplication also merges by weak identity. `DeduplicationService.groupByNameSimilarity`, `areNamesSimilar`, and `mergeGroup` collapse candidates by normalized names, initials, partial first names, and longest name. That is reasonable for display cleanup, but it is unsafe as a person-resolution method. `mergeGroup` also takes max h-index/citations from grouped candidates, which would be dangerous if bibliometrics ever entered before a stricter identity boundary.

Finally, persistence accepts enriched identity fields as ordinary candidate attributes. `pages/api/reviewer-finder/save-candidates.js` `handler` writes ORCID, Scholar ID, Scholar URL, and metrics from `candidate` or `candidate.contactEnrichment` without any identity-confidence status. `pages/api/workbench/enrich-recommended.js` does the same through `ContactEnrichmentService.enrichCandidates` and id-keyed writeback. There is no "abstained identity," "ambiguous identity," or "human review required" state before bibliometrics/contact fields become durable.

## 2. Proposed architecture

Keep candidate discovery broad, but split the pipeline into three explicit stages: candidate generation, identity disambiguation, and contact-detail resolution. `DiscoveryService.searchPubMed`, `searchArXiv`, `searchBioRxiv`, and `searchChemRxiv` should remain candidate-generation tools. They are good at finding names attached to relevant papers. They should stop pretending to produce resolved people. The output should be a `candidateHypothesis`: target name, claimed/suggested institution, expertise terms, seed publications, source, and reason.

The new middle stage should be a dedicated identity resolver, used by both `pages/api/reviewer-finder/discover.js` and `pages/api/workbench/enrich-recommended.js` before contact enrichment. It should produce a `resolvedIdentity` object with `status: confirmed | probable | ambiguous | unresolved | rejected`, `confidence`, `anchors`, and `evidence`. Anchors should include ORCID iD, Google Scholar author ID, institutional email/domain, DOI/PMID publication cluster, faculty page URL, and known affiliation history. The key change is that h-index, citations, email, and website are not allowed to attach to the candidate unless the identity resolver says the source belongs to that human.

For Scholar specifically, replace the current first-result approach in `SerpContactService.findScholarProfileViaGoogle` with candidate profile scoring. The resolver should collect several Scholar-profile search results, extract the displayed profile name, URL author ID, snippet affiliation, and visible terms, then require the displayed Scholar name to match the target name under a strict name comparator. This directly solves the Tsai/Nakano case: "Masayuki Nakano" fails the name guard for target "Li-Huei Tsai" even though the snippet contains MIT and Li-Huei Tsai Lab. Institution match becomes supporting evidence, not permission to attach metrics.

For ORCID, `ORCIDService.searchByName` should return candidates, not select the top one in `findContact`. The resolver should score each ORCID record against target name, other names, current/past affiliations, public email domain, researcher URLs, and works if available. If ORCID has a public DOI/work list that overlaps with PubMed/Crossref seed publications, that should be a strong positive anchor. If the ORCID name differs materially and only affiliation matches, it should not be selected.

For publication identity, build a DOI/PMID co-authorship fingerprint. `DiscoveryService.verifyClaudeSuggestions` already collects PubMed articles for the target author name. That cluster should become evidence: repeated coauthors, journal/topic distribution, affiliations over time, and DOI list. Crossref can be used to enrich DOI metadata and sometimes expose author ORCID IDs or affiliations; coverage is inconsistent, so the resolver should treat those fields as opportunistic evidence, not guaranteed API output. The value is that a Scholar or ORCID profile can be checked against the same publication cluster rather than against just name plus institution.

Contact resolution should run only after identity is pinned. `ContactEnrichmentService.enrichCandidate` should consume `resolvedIdentity`, not raw `candidate`. PubMed email extraction from `ContactParser.extractContactFromPublications` should only use publications that belong to the resolved identity cluster. `SerpContactService.findContact` should verify that a faculty page's page title/snippet/name matches the resolved person and that email domain is compatible with current or past affiliation. This prevents contact details for lab members or homonyms from attaching to the intended reviewer.

Ranking must also change. `lib/utils/relevance-score.js` `scoreRelevance` currently rewards h-index and citations, but it cannot tell whether those metrics are safely attached. The scorer should only use bibliometrics when `resolvedIdentity.status` is confirmed or high-confidence probable. Ambiguous candidates should still appear, but with a visible identity warning and no metric boost. This directly removes the incentive for wrong-but-rich profiles to float to the top.

## 3. Hard case handling

Same-institution lab members require a hard name guard and role-sensitive evidence. The Tsai/Nakano case should fail because `SerpContactService.findScholarProfileViaGoogle` would return a Scholar displayed name that does not match the target name. Lab-name mentions in snippets should be treated as weak or even suspicious evidence when the lab name contains the target PI's name but the profile name differs. Institution match should not override profile-name mismatch.

Common names and homonyms require abstention by default. For "Wei Zhang," a PubMed name search in `DiscoveryService.buildAuthorQuery` can easily collect papers from multiple people. The resolver should detect fragmented affiliation clusters, multiple ORCID records with similar scores, multiple Scholar profiles with matching names, or publication clusters with unrelated coauthor networks. In those cases, status should be `ambiguous`, and the UI should show competing identities instead of selecting one.

Name variants need controlled flexibility. `DiscoveryService.generateNameVariants` is useful for nicknames and initials, and `filterToMatchingAuthorMultiVariant` is a good start, but the same flexibility is unsafe for profile identity. The resolver should distinguish "publication author-line matching" from "profile owner matching." Initials can help gather candidate publications, but a Scholar or ORCID profile should require a stronger match: full family name plus compatible given name, credit name, other names, or known transliteration. Maiden-to-married names should be accepted only when there is corroborating evidence such as ORCID other names, shared DOI cluster, faculty page biography, or institutional page.

PIs who publish less than trainees should not be penalized by publication-count heuristics alone. `DiscoveryService.verifyClaudeSuggestions` currently requires `MIN_PUBLICATIONS = 3` in recent years for verification. That makes sense for active reviewer discovery but is not an identity proof. For a known PI, a faculty page, ORCID iD, institutional email, and older landmark publications may be enough to confirm identity even if recent PubMed volume is low. The resolver should separate "identity confirmed" from "reviewer activity/relevance score."

Stale affiliations require temporal reasoning. `DiscoveryService.extractBestAffiliation` returns the most common affiliation, not necessarily current affiliation. `SerpContactService.institutionConflicts` treats conflicting institution snippets as a likely wrong person, but a PI may have moved. The resolver should allow past-affiliation matches when the publication cluster and name are strong, while marking current contact details as stale until a current institutional page, ORCID current employment, or recent email domain confirms the current location.

Co-author confusion needs explicit negative signals. If the target appears frequently as a coauthor of a profile owner, that is not the same as being the profile owner. The resolver should treat a source result whose visible name differs from the target but whose snippet includes target-name lab/coauthor terms as a rejection, not a match. This is the persistent pattern behind trainee-vs-PI confusion.

## 4. Pragmatic phased adoption

Phase 1 should be quick wins with no new APIs. Add a strict displayed-name guard before accepting Scholar metrics in `SerpContactService.findScholarProfileViaGoogle` / `ContactEnrichmentService._attachScholarMetrics`. If `scholarName` does not match `candidate.name`, skip metrics and record `tierResults.scholar_profile.skipped = 'name_mismatch'`. Also add an identity status field to enriched results and prevent `save-candidates.js` and `workbench/enrich-recommended.js` from persisting Scholar metrics unless identity is at least probable. This directly fixes the live Tsai/Nakano class without a large rewrite.

Phase 1 should also make ORCID safer by changing `ORCIDService.findContact` semantics conceptually: do not take the first result with email just because it exists. Score returned ORCID records by exact/variant name match first, then affiliation and public URLs. If multiple records are plausible or the top record lacks a strong name match, return `ambiguous` or `null`. This solves same-name homonym and wrong-email risks while keeping the current ORCID API.

Phase 2 should introduce the shared identity resolver service and make it the contract between discovery and enrichment. `DiscoveryService.verifyClaudeSuggestions` should output publication evidence and suggested identity hints, then the resolver should run ORCID, Scholar, PubMed DOI/PMID cluster checks, and optional Crossref DOI metadata. `ContactEnrichmentService.enrichCandidate` should accept a resolved identity and refuse to fetch/persist metrics for unresolved identities. This structurally solves the current design flaw where enrichment sources are treated as authoritative independently.

Phase 2 should also change UI data shape. Discovery results should show identity confidence separately from relevance. A candidate can be highly relevant but unresolved. A candidate can be identity-confirmed but low relevance. `relevance-score.js` should stop counting bibliometrics unless `resolvedIdentity` is trusted, and it should never turn confidence into a hidden sort-only field. Staff need to see why the system selected or abstained.

Phase 3 can improve quality with richer evidence and caching. Use Crossref DOI metadata opportunistically for author ORCID IDs and affiliation fields when present; not assuming universal Crossref coverage. Cache resolved identities by stable anchors: ORCID iD, Scholar author ID, institutional email, and verified DOI cluster, not by name alone. Add a review queue for ambiguous identities so staff corrections can create durable identity anchors for future searches.

The cost and latency tradeoff is manageable. Phase 1 adds almost no cost and may reduce SerpAPI metric calls because wrong Scholar profiles are skipped earlier. Phase 2 increases latency because each selected candidate may need multiple ORCID/Scholar/Crossref checks, but it can be bounded: run deep identity resolution only for candidates displayed above a threshold or explicitly selected for enrichment. Wrong-but-confident persistence is more expensive than an extra second of identity checks.

## 5. Open questions, risks, human-in-the-loop

The system should abstain whenever the strongest evidence is name plus institution only. That exact signal failed in the Tsai/Nakano case. It should also abstain when Scholar profile name mismatches, ORCID returns multiple plausible records, PubMed publication clusters split across multiple affiliations/coauthor networks, or current contact details cannot be tied to the resolved identity. These should be first-class statuses, not silent skipped fields.

ORCID coverage is uneven. Many researchers have ORCID records with no public email, sparse works, stale employment, or no useful affiliations. Scholar coverage is also uneven and SerpAPI access to Scholar author data depends on the profile author ID; profile search uses ordinary Google search while metrics use `google_scholar_author`. Therefore the system cannot require ORCID or Scholar for every candidate. It should require enough cross-source agreement before attaching high-impact fields.

Crossref is useful but not a silver bullet. It can help connect DOI metadata, author names, and sometimes ORCID/affiliation evidence, but coverage varies by publisher and record. The plan should treat Crossref as corroboration for DOI clusters, not as a universal identity database. PubMed remains stronger for biomedical author affiliation/email evidence, but PubMed author names are not globally unique.

Human review is the right answer for ambiguous but valuable candidates. The UI should show "identity unresolved" with competing evidence: possible ORCID records, possible Scholar profiles, matched publications, and why the system abstained. Staff should be able to choose the correct identity, reject all, or save the candidate without bibliometrics. That manual choice should persist stable anchors so future runs do not repeat the ambiguity.

There is also a data governance risk. `save-candidates.js` and `workbench/enrich-recommended.js` currently write identity-bearing fields into Dataverse. Once wrong Scholar IDs and metrics are persisted, later runs may inherit a false identity. The migration plan should include a way to mark existing Scholar/ORCID fields as unverified unless they were produced after the new resolver, especially for records enriched through the current `ContactEnrichmentService._attachScholarMetrics` path.

**Executive summary:** keep the broad reviewer discovery machinery, but stop treating discovery and enrichment as identity resolution. The fastest safe fix is a hard Scholar displayed-name guard plus no persistence of metrics without identity confidence. The durable fix is a shared identity resolver that scores ORCID, Scholar, DOI/PubMed clusters, email domain, affiliations, and source agreement, with an explicit abstain path. The guiding principle should be: unresolved is acceptable; wrong and confident is not.
