# Prompt descriptions and current callers audit

The Admin prompt editor can show useful descriptions without changing the machine keys or prompt instructions. It should also say where a prompt is used and whether the stored row actually controls an application path.

[VERIFIED via the read-only Production inventory and source searches described below] The inventory contains **40 distinct names across 59 versions**: **34 with application callers, four stored Phase II references without a current application reader, one draft-only name, and one developer diagnostic**. Of the 40 names, 39 have a sole current row; `phase-i.checkin` has none. A current row is a publication flag, not evidence of application use.

## Scope and evidence

- Audit date: October 29, 2026. Source snapshot: `f26145c0feff64c9d7da2f831471dba67c6fa3a5`. The subsequent calendar wording merge does not change the prompt surfaces covered here.
- Entry point: Admin → AI → Prompts (`/admin?workspace=ai&view=prompts`) → `GET /api/admin/prompts` → `listPrompts` → `wmkf_ai_prompts`. Execution readers are the shared Executor, Reviewer Finder resolver, and tool-app resolver.
- Persistence inspected: existing Dataverse prompt rows, including system/body text, variable declarations, output schemas, versions, current flags, and notes. No application or prompt changes, Production writes, model calls, or diagnostic executions were made.
- Live probe: app client credentials were used only to obtain a Dataverse access token and GET `wmkf_ai_prompts`, selecting configuration fields, ordered by name, with a 300-row ceiling and bounded pagination. The result was 59 rows, no next page, 40 names, 39 sole-current rows, and no duplicate-current names. The report retains only names, versions, descriptions, and source references; no tokens, real record IDs, raw prompt bodies, applicant content, or run outputs.
- Source search domain: `lib`, `pages`, `shared`, `scripts`, `tests`, and `.github`. Literal names, constant-based dispatch, dynamic perspective-name construction, resolver calls, and caller/worker chains were checked. An application caller means a path present in this source snapshot; it does not assert recent execution, an enabled Production feature flag, or access for every staff member. External consumers such as Power Automate were not audited.
- `listPrompts` represents a name by its current row, or by its latest non-current row when it has no current version. The current live inventory is below the reader's per-query cap. Evidence: [inventory service](../../lib/services/admin/prompts-list-service.js), [prompt adapter](../../lib/dataverse/adapters/ai-prompt.js), [API route](../../pages/api/admin/prompts/index.js).

## Findings

1. **The page exposes implementation keys without purpose or callers.** [VERIFIED via `PromptTemplatesSection.js` `PromptPanel`, and `prompts-list-service.js` `mapRow`] Cards display the technical name, version, size, timestamps, and budget. The response has no dedicated display-title, description, usage-status, or caller fields. The `wmkf_ai_notes` column is not selected or returned by this list path.
2. **Publication and use need separate labels.** [VERIFIED via live rows and the caller matrix] All four `phase-ii.*` rows are current but the corresponding routes use code-generated or inline templates. `phase-i.checkin` is draft-only and no invocation was found. `executor.echo-parity` has a developer test caller, not an application caller in the searched source. None should be removed merely on the basis of this audit.
3. **Existing notes are not a reliable description source.** [VERIFIED via live notes and current route/service calls] `peer-review-summarizer.analyze` still says the live route uses a generator “until route refactor,” but `/api/process-peer-reviews` now calls the stored prompt through the Executor. `reviewer-finder.score-candidates` has a similar “legacy ... until route refactor” note, but `ClaudeReviewerService` resolves its stored body. Seed notes mix development history with purpose, and many republished current rows have no notes. Do not copy them wholesale into user-facing descriptions.
4. **Similar names hide different jobs.** [VERIFIED via current prompt content and the matrix] AI Review Panel seat/chair prompts produce simulated AI reviews; review synthesis summarizes submitted human reviews; uploaded peer-review summarization is a separate tool. Meeting presentation summaries and staff-only discussion summaries also need distinct titles.
5. **Editing a stored row does not guarantee that exact body runs on every call.** [VERIFIED via `reviewer-prompt-resolver.js` and `tool-prompt-resolver.js`] Reviewer Finder permits a validated per-user body override and has code fallback paths. Tool apps read stored templates but can use bundled definitions during qualifying transient failures. The four Phase II rows have no connected stored-row reader. A description should not imply that every card is the sole runtime source in every circumstance.

## Suggested presentation

[PLANNED] Give each card a descriptive title, one sentence explaining its task, and a **Used by** line in product language. Keep the technical key visible as a secondary identifier so staff can relate it to source and support conversations. Put exact service/route references behind a “Technical callers” disclosure.

For example:

> **Executor echo and cache diagnostic**
>
> Copies test inputs into JSON so developers can compare Executor output and observe cache use.
>
> **Used by:** Developer smoke tests
>
> **Status:** Developer diagnostic
>
> `executor.echo-parity`

Use separate badges for **Application caller**, **Stored reference**, **Draft only**, and **Developer diagnostic**. Keep the existing current/draft version state as an independent fact. For a stored reference, say “This stored row is not connected to the current application route.” Do not label it “safe to delete.”

[PLANNED] The smallest implementation is a reviewed, code-owned metadata map keyed by the existing prompt name, attached to the read-only list response or read directly by the Admin component. This can add titles, descriptions, and a curated caller list without changing the Dataverse schema, prompt keys, prompt text, or publication history. The UI should retain unrecognized live names with “Description not cataloged” rather than hide them. An exact inventory-to-catalog comparison should identify uncataloged or removed names at review time. Caller links are maintained evidence, not an automatically complete runtime dependency graph.

This recommendation is a source-supported design proposal, not a built or tested implementation. Editing descriptions directly in Admin would be a separate metadata-ownership decision; existing notes and versioned prompt publication should not be repurposed silently.
