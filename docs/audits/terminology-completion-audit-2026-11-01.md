## Autonomous release-verifier instructions and limits

From the repository, with Node.js 24 or newer and an already-authenticated GitHub CLI OAuth session, run:

```sh
npm run --silent verify:terminology -- --expected-sha=<full-40-character-commit-SHA>
```

The script `scripts/verify-terminology-release.mjs` checks GitHub's latest Production deployment and status, requiring the exact expected SHA and `success`. It then compares the checkout against that commit, including unstaged, staged, and non-ignored untracked files under `lib/`, `shared/`, `pages/`, `modules/`, `package-lock.json`, `next.config.js`, `proxy.js`, `vercel.json`, and `scripts/lib/use-extensionless.mjs`. `package.json` metadata and dependencies are compared from index and worktree, excluding only the verifier's own `scripts['verify:terminology']` command alias. Its 22 unit tests exercise clean and dirty worktrees, staged/index-masked and untracked runtime edits, dependency drift, deployment SHA/status failures, and mutations to guard status/code/message/body/calendar behavior. Finally it locally imports `normalizeComposeInput` with `fetch` disabled and runs nine synthetic cases: retired material links; retired `docx`, `pdf`, and `both` attachment modes; unknown attachment mode; omitted, blank, and `none` current-client modes; and current calendar selection. Rejected cases assert the exact HTTP status, code, message, and body; accepted cases assert normalized fields.

It does not load application environment files, authenticate to the application, send application HTTP requests, mutate live state, or verify browser-rendered error copy. It does make read-only GitHub API calls for deployment metadata. The [clean JSON receipt](terminology-release-verification-2026-11-01.json) records the passing deployment/source/synthetic checks and explicitly sets `liveApplicationRequests` and `liveErrorResponsesTested` to `false`. This is not live route acceptance.
