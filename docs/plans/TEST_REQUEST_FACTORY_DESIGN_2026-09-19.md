### Owner decisions

1. **[OWNER DECISION] Numbered proposal PDFs are copied and renamed.** `Reviewer Materials/Proposal_<n>.pdf`, `AI Materials/ProposalNarrative_<n>.pdf` and `AI Materials/ProposalBibliography_<n>.pdf` are copied byte-for-byte under the destination request number. The owner reports that the request number is not currently written into these generated PDFs; if it is in future, a mismatch inside a test fixture is acceptable. No identity-rewriting transformer is required for them. Contents matter only insofar as the files exist for workflows to process (for example emailing them).
2. **[OWNER DECISION] Later-stage clones.** The administrator chooses how far along the Workbench (left to right) the clone should reach, and the factory brings the documents created along the way. Documents are **linked** where feasible (registry row, request pointer and any parent records, so the app treats them as the new request's documents); where a copy cannot be linked, the factory drives the app's own no-AI step to produce the document in the new request. See *Later-stage recipes* below.
3. **[OWNER DECISION] Reviews are cloned onto synthetic reviewers** so they appear as ordinary reviews in the new request. Synthetic reviewers are seeded 1:1 from the source request's reviewers (the source is expected to be a test request itself).
4. **[OWNER DECISION] Synthetic reviewers use real, staff-controlled throwaway inboxes** so staff can exercise reviewer interactions (invitation, portal, submission, thank-you). Each staff member has different throwaways, so the addresses are **editable per run in the creation form**. When the source reviewer is already synthetic, the field defaults to that reviewer's address; when the source reviewer is a real person, the field starts empty and is required — a real reviewer's address is never used as a default. The per-run assignment is recorded in the run ledger. There is no central address list to maintain.
5. **[OWNER DECISION] Sandbox first, production soon.** Live runs start in the Dataverse sandbox. The source for sandbox testing is production test request **1003222** (ZZTEST-03), because no production request has completed the whole workflow; the owner authorized read-only production reads scoped to that request (2026-09-23).
6. **[OWNER DECISION] Cross-environment source bundle (option A).** For sandbox runs, a read-only production step exports what the factory needs from the source into a private local bundle; a sandbox step builds the new request from that bundle. The same reader and builder serve the eventual same-environment production path; neither is sandbox-only scaffolding. SharePoint is the shared akoyaGO site in both cases, so file copy is not cross-environment.
7. **[OWNER DECISION] Build ownership.** Claude (root) now builds this workstream in the `codex/test-request-preview-integration` branch (worktree `WMKF_Apps-factory`). Codex performs an adversarial review of each stage before root accepts it. This replaces the Luna-builds / Sol-reviews arrangement below.

### Synthetic reviewers

[VERIFIED via read-only source investigation, 2026-09-23] A review "exists" through a `wmkf_potentialreviewers` person row, a per-request `wmkf_appreviewersuggestion` row, `wmkf_appreviewanswer` rows keyed by (suggestion, question key), and a review DOCX pointer on the suggestion.

- **Person:** a `wmkf_potentialreviewers` row named `TEST · <source reviewer name>` with the run's throwaway address (decision 4), created through the existing find-or-create by email so re-cloning reuses it. A person-level test marker is required; the address alone is not a safety boundary.
- **Suggestion:** copy candidate content, lifecycle and received state; regenerate `wmkf_grantcyclecode` from the destination; never copy portal tokens, proposal URL/password or `wmkf_honorariumrequest` (it points at the source's BILL request).
- **Answers:** copy, bound to the new suggestion.
- **Writer:** the repository's reviewer-engagement boundary gate permits generic suggestion writers only inside `lib/services/reviewer-engagement/`, so the seeder is a new named command there. Order: preallocate and journal the suggestion GUID; create it without the received stamp; upsert answers; then stamp received (and thank-you, when the thank-you email is not wanted) with If-Match. Stamping received before answers exist reproduces the zero-answer snapshot left by test Request 1003223.

## Outcome and user flow

From an existing request, an administrator selects **Create test request**. A short wizard asks for a test label, starting point, selected documents, and staff-controlled test identities. It previews exactly what will be copied, reset, created, and omitted, including the destination environment. One **Create test request** action produces a new request and opens it in the Workbench with a persistent TEST banner and a link to its creation receipt.

A bounded source/script search found existing tests using prebuilt requests, but no reusable admin clone tool. **[VERIFIED via Luna source reconnaissance; not a tenant feature inventory.]**

The tool supplies the repetitive setup. The user should not need to construct a Dataverse request, arrange SharePoint folders, repair document pointers, or send an invitation to establish a test fixture. Defaults come from a configured test organization and test personas; no contact is silently inherited from the source. (Amended 2026-09-23: synthetic reviewers are seeded from the source's reviewers with per-run editable throwaway addresses; see Owner amendment decision 4.)

The owner explicitly chose fresh destination Requests rather than resetting existing fixtures. SharePoint documents and version history survive Dataverse state resets and can affect later behavior. Every factory run therefore owns a fresh Request GUID/number/location/folder/history under W. M. Keck Foundation; resetting an existing Request is not the default or a fallback.
