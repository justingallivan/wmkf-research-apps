## 5. Proposed storage and contracts

**PLANNED architecture, subject to implementation preflight.** Dataverse continues owning business identities, cycle settings and request-document references. SharePoint owns files. Postgres owns durable delivery/job/email receipts. No migration number is reserved by this plan.

- Versioned cycle configuration keyed by meeting-date cycle code (e.g. D26) + Research Grant Program GUID: dedicated versioned system-setting keys for dates/roster/registered target/recipients, strict parsing and bounded payloads, using `setSettingIfUnchanged` and admin-only routes. Do not use grant-cycle customFields: their writer lacks ETag fencing and external-review email consumers use those fields. Confirm setting size limits before implementation. Daily operational timestamps do not rewrite settings. The Research identity starts from `BOARD_COPY_PROGRAM_ID` in the old configuration and must be verified against Dataverse program metadata; never derive scope from the handoff-email allowlist. Do not assume a join to appgrantcycle GUIDs. A roster request whose meeting date changes is flagged for audited admin resolution, never silently removed.
- Explicit CSO and Grants Manager bindings in separate versioned system-setting keys, with revision-fenced admin writes; leave staffing v2 and its exact-key readers unchanged. Release actor must equal enabled configured CSO and remain eligible in trusted staff data. Archive/reconcile actions accept an enabled authorized admin OR enabled configured Grants Manager; checks apply in UI, route and worker. Grants Manager role alone cannot edit assignments, release as CSO, or acquire general Admin privileges. Re-read assignments for unstarted operations and future email sends; preserve historical actor/recipient snapshots. Never trust client role, recipient, drive ID or source URL.
- Cycle-run ledger: fixed program/cycle identity, first-event timestamp, setup revision, reminder state, archive state. The earliest successful release or leadership event is recorded idempotently; reconciliation recovers a missed cross-store event from persisted leadership checkpoints across all Final rows, including superseded rows, not just current-Final pointers. Validate historical cycle attribution; changed meeting dates require review rather than assigning an old event to the wrong cycle. Existing active cycles bootstrap from earliest eligible timestamp, not cron lookback or deployment date. No history email burst on activation.
- Expected membership is persisted by request identity/revision. Progress = successful release receipts intersected with expected membership; unmatched receipts remain visible rather than hidden. An unconfirmed/empty roster cannot satisfy “all done”.
- Release receipt unique by cycle + program + request, with approved actor/time, source artifact/drive/item/version/ETag/hash, reserved name, destination identity, lease, upload intent, exact error and completion. One approval owns one source selection; a version change before bytes are captured requires re-selection, not silent approval of changed bytes. Use current-file download with before/after version and ETag checks plus a content hash; changed versions require re-selection. Do not assume the historical-version helper can download the current version. No private byte-staging store in this phase. Once upload has begun, reconcile the existing intent instead of starting a new approval/upload.
- Email receipts: daily Beth/post-Board reminders unique by cycle + kind + local date; failure alerts by cycle + run + failure revision; completion by cycle + completed archive revision. Each receipt stores the resolved To/cc identities and one activity-level accepted-send state (not proof of delivery to each person); deduplicate overlapping roles. A changed role assignment changes future unsent notices, not a second same-day send or an already accepted receipt. Persist intended content snapshot, activity/correlation ID and accepted state. Reconcile ambiguous send outcomes; never blind-resend on timeout. Re-read current completion immediately before dispatch. A late concurrent release may produce one already-prepared reminder; subsequent runs stop. User-configurable recipients are resolved to eligible internal identities server-side. If To or the required Grants Manager binding cannot be resolved to eligible staff, hold the email and surface an operational alert; never silently promote cc to To or omit a required recipient.
- Persist archive-start confirmation and durable run creation in one Postgres transaction: lock the cycle/program row, require `archive_started_at IS NULL`, insert one uniquely constrained initial run per cycle/program and set the timestamp; retries return the same run. Stop confirmation reminders only after commit; a rejected request leaves reminders active. Worker failure produces an idempotent alert, never a success email or resumed confirmation reminders. Re-read start/completion before email dispatch; reconcile ambiguous sends and retain accepted history. Completion flag is committed only after all entries are archived or approved exclusions, and drives a durable completion-email intent recoverable after a crash.
- Archive run/entry receipt keyed by cycle/release + frozen source version; generation key makes Request Document creation recoverable. Track source identity/version/hash, destination item, registry row, actor/time and each stage. No JSON body can select arbitrary destination or bind another request.
- Board archive registry: propose a distinct `BOARD_WRITEUP` artifact type with a dedicated producer, cycle and source lineage, using existing Ready operation state and a clearly documented lifecycle. Allocate option value only after schema/consumer audit. Provision schema-as-code, readiness gate and reverse maps; do not overload `FINAL_WRITEUP` and accidentally enter current-Final selectors. Archive does not change `_wmkf_currentfinalwriteup_value`.

## 8. Reconciliation and archival protocol

List all children with pagination in the exact cycle target; compare with successful release ledger identities. Same-ID rename is present; moved outside cycle folder is reported even if recoverable by ID. Missing/deleted, unknown/replacement ID, duplicate mapping and unrelated extra file are separate results. Equal counts are insufficient. Missing email identifies request number, institution and original filename, links admin reconciliation; repeated identical runs do not spam duplicates. Changed discrepancy set has a new revision.

Before archive start, reconcile confirmed expected membership against successful release receipts as well as SharePoint files. An expected but never-released request must be released or explicitly resolved by an audited roster correction before the cycle closes; do not silently exclude it from the completion calculation. Preserve original roster and all reasons in the report. Beth's reminders stop only when current confirmed membership is fully released, including after an explicit audited correction—not merely because archival is requested. The completion email includes original/adjusted expected counts, released/archived/excluded counts and any requests removed without release.

An authorized admin or Grants Manager confirms resolved exceptions and the final source manifest under a revision fence. Freeze each source file's version/ETag; revalidate at execution. Concurrent changes invalidate that entry and require renewed confirmation; this blocked state raises the archive-failure alert and never silently waits or restarts daily confirmation reminders; no silent import of later edits. Copy, never move/delete, the approved edited file to its server-resolved request SharePoint folder under a cycle-specific Board-writeup name. Use create-only intent/receipt guarantees again, explicitly passing fail-on-conflict because the general upload helper defaults to replace. Evaluate the existing Board Milestones request subfolder during destination preflight. Commit/reference a new Dataverse Board Writeup row only after file validation; complete archive entry only after independent registry readback. Cross-store transaction failures resume from known item/registry IDs; never recopy blindly or show an unbound file as archived.

After archival, further edits in the shared Board Materials folder do not change the preserved request copy. Correcting an archive requires a separately authorized versioned correction; no automatic overwrite. The record represents the admin-confirmed Board version; it does not claim independent proof of the exact Diligent bytes. Staff must confirm that these are the Board-used versions.
