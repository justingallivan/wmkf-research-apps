## 3. Proposed physical schema

All names/types in this section are implementation proposals, not live schema claims.

### Dataverse Expertise Profile

- Primary GUID; required display name (255 characters); standard state/status for Active/Inactive; standard created/modified metadata and auditing enabled.
- Required category Choice: Research Program Staff, Consultant, Board. Allocate actual numeric values during schema specification and use symmetric read/write mappings.
- `leadPdEligible`: Boolean, default false. Effective eligibility additionally requires active profile, staff category, and a valid enabled User link. This setting grants no app permissions and assigns no requests.
- Nullable User lookup for staff; nullable Contact GUID reference for external profiles (not a native relationship; see deletion semantics below). Enforce role/link compatibility server-side. Contact is never required for external profiles. A staff profile can be staged without a User but cannot become lead-eligible.
- Optional title, affiliation, ORCID, preferred email, primary fields, keywords, specialties, methods, distinctions, expertise summary, Keck affiliation and Keck-affiliation details. Preserve source values losslessly, including empty/null distinctions where behavior depends on them. Match or exceed existing field lengths; text sizing is verified from the full import dry run before schema application.
- No program, Short ID, Match Type, scheduled dates, or new Matching Guidance column in this slice. A future content decision may add guidance explicitly.
- Native optimistic concurrency/ETag required for edits. Disable/delete are different operations: app supports deactivate/reactivate; hard-delete is not exposed. Configure permissions and relationship behavior to protect referenced profiles from deletion.

**Duplicate enforcement:** each User/Contact may be linked to only one profile (including inactive profiles); reactivation reuses it. This strengthens today's active-only Contact uniqueness and requires an explicit duplicate reconciliation before import. User identity remains a native lookup with an alternate key; Contact identity is a nullable Single Line of Text column of length 36 containing only a validated canonical lowercase, hyphenated GUID, with its own alternate key. Empty references are null, never empty strings. App writes canonicalize; readers reject malformed/noncanonical direct edits. Verify uniqueness for these exact column types in sandbox; do not rely on an app preflight query alone. Unlinked profiles cannot be conclusively deduplicated by name: flag possible duplicates for human review; never merge automatically. If retained duplicates prevent these keys, resolve the data or return the design for review rather than inventing a merge policy.

**Contact deletion/merge semantics:** preserve the existing GUID-reference behavior rather than introduce a native Contact lookup with implicit cascade rules. A deleted/inactive/missing Contact leaves the stored GUID intact and yields no email; it must never silently revive preferred email. No roster relationship blocks CRM deletion. Contact merges do not auto-relink profiles: show the stale link for explicit staff repair to the survivor, with duplicate checks. Staff deliberately clearing a link explicitly reviews the manual address before using it. Sandbox tests cover delete, merge, inactive, missing email, and deliberate unlink. The Contact picker remains the UI. This is an engineering choice to preserve the existing link contract.

**Keys and permission enforcement:** prove multiple null values are permitted for the optional User lookup and optional Contact text reference in sandbox; verify every required alternate key is Active before import. If unsupported, stop and revise the schema (a separate non-null identity reservation table is the candidate fallback); do not deploy query-only uniqueness. Category changes atomically clear incompatible links and disable lead eligibility; require the editor to review that consequence. Readers fail closed on invalid direct-Dataverse edits. Preserve actor attribution through explicit acting-user context or a dedicated last-app-editor User field if native modifiedby remains the service principal; verify chosen behavior in sandbox and show native direct-edit attribution separately.

### Postgres identity bridge

The Atlas documents a shared Preview/Production Postgres database. Verify current bindings before rehearsal; never assume separate databases. Use a numeric identity table (proposed `expertise_roster_identity`, primary key `id`) as the feedback FK target, plus a binding table keyed by `(roster_id, target_host)` with unique `(target_host, dataverse_profile_guid)`. The server derives target_host from the actual resource URL used by the roster adapter, normalizes its hostname, and requires membership in the tracked target registry even if the general interlock is off; never accept it from request input or a different service’s URL precedence. These tables hold no editable expertise, names, emails, or eligibility copies. Dataverse owns roster information.

No bridge ID allocation or FK change is permitted on shared Production Postgres during preparation or rehearsal. Import existing numeric IDs unchanged into the identity table. Explicitly reconciled counterparts may bind the same numeric identity in sandbox and Production. A new sandbox-only person receives a new globally allocated number but no Production binding: Production must report that identity unavailable, never use the sandbox GUID or a name match. Never overwrite one environment's binding with another's. Advance the sequence past BOTH the largest ID and the old roster sequence high-water mark; sequence gaps are harmless.

Retarget `consultant_feedback.consultant_roster_id` FK to the numeric identity table after every referenced ID is present. Preserve existing numeric client DTOs and Site Visit/meeting JSON references. Return canonical GUID explicitly for integration. Resolve each numeric reference only within the current trusted Dataverse target. New identities remain globally distinct even with shared Postgres.

Dataverse create and Postgres mapping are not atomic. Use a required stable creation-key text column with an Active alternate key: interactive creates use `app_<mutation UUID>`, while imports use `legacy_<source-dataset UUID>_<legacy numeric ID>`. The source-dataset UUID is fixed in the import manifest for this source lineage, not regenerated per attempt or delta; sandbox clones retain the source lineage but target their own Dataverse org. These machine keys are internal idempotency metadata, not the rejected user-facing Short ID. Import retries use create-if-absent by key, then GET the same row after an uncertain response and compare the expected payload; mismatches stop for reconciliation rather than blindly overwriting intervening edits. Direct Dataverse creates must populate a distinct `direct_<UUID>` key or remain quarantined until repaired. Use this key to make replay find the same profile after a lost response, then idempotently ensure its numeric identity/binding in a local transaction. Unique `(target_host, profile_guid)` prevents concurrent replay creating two usable bindings; a losing transaction rolls back its unused identity. Report interrupted completion as retryable, not fully saved. For profiles created directly in Dataverse, provide explicit reconciliation before dependent app use. Never silently fall back to the old roster.

Per-consumer unavailable/invalid handling (a transport failure or incomplete paginated read is a whole-read error, not evidence of absent profiles):

| Consumer | Complete-read row lacking a numeric binding | Structurally invalid row / invalid role-link combination |
|---|---|---|
| Roster administration | Show by GUID with reconciliation warning; edit by GUID | Show repair warning; do not hide the record |
| Expertise matching | Numeric binding is not required; use canonical profile GUID | Omit from model input and explicitly report excluded profile(s); if no usable roster/candidates, return an explicit unavailable/no-recommendation result |
| New recipient directory | Omit that row and display an exclusion warning; other valid recipients remain usable | Same; missing/unusable email also prevents delivery, not advisory matching |
| New feedback picker | Omit and warn; reject a submitted unmapped numeric ID | Same; inactive/non-Consultant cannot be a new author |
| Existing feedback attribution | Retain feedback with visible unavailable identity; no name guessing | Same; inactive but valid mapped profiles still resolve |
| Existing selected attendee refs / send | Fail the requested send if any selected ref cannot resolve; never drop attendees silently | Same |

A Contact GUID that is valid but points to a missing/inactive Contact is a contact-health problem, not grounds to remove the person's expertise from advisory matching. Effective lead eligibility separately checks enabled User identity. Backend warnings must be rendered by each consuming UI; an empty result must not conceal exclusions. Preserve the existing generic `Consultant` attachment filename fallback when author display cannot be hydrated, with a visible warning; identity display is not attachment authorization. Post-commit feedback hydration failure returns the saved row with unavailable attribution rather than reporting that the committed save failed. Tests prove target isolation and each row-level/whole-read distinction.

4. Replace every feedback SQL join to the old roster with batched identity hydration, including list, create replay response, update, attachment filename generation, and shared briefing readers. Only a new create remotely validates the selected active Consultant, then performs the local transaction/ON CONFLICT and rereads the winner. **This intentionally improves current behavior:** today eligibility runs before the conflict insert and can reject a replay after retirement. Test the concurrent winner as well as sequential replay.

   For update, perform an unlocked pre-read of the author tuple, determine the resulting author and validate remotely only if it changes to a roster consultant. Rollback rehearsals run only on the dedicated database.
