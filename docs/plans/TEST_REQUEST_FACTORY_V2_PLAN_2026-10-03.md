## Recovery policy

The shipped first slice adds a **read-only, server-derived diagnosis** using the owned run row and recorded resource receipts only. It does not read private artifacts or live external systems. A future separately approved extension may read the authoritative run row, typed resource journal, private artifact presence/digest/freshness, lease state and the minimum live readback needed to describe a safe next step. It must not call the current status-recheck operation: that operation may write late-effect ledger data for already complete or needs_attention changes, so it is not read-only; it does not change dispatched status. The client cannot choose a run status, destination, item ID, write-attempt flag, or recovery decision. The response should state the stopped step, evidence present/missing and one disposition: **retry under existing runner**, **wait/re-inspect**, **readback verification may be evaluated**, **start a new run**, or **blocked for operator investigation**. Unknown state stays blocked. Return finite safe reason copy and identifiers already needed by the owner; never return bundle contents, purpose/abstract text, bearer links, recipient addresses or raw upstream error text.

| State evidence | Existing behavior | V2 disposition |
|---|---|---|
| No dispatch marker | Existing retry can re-run after preconditions are checked. | Preserve existing retry path and explain why it is allowed. |
| Dispatch marker but no recoverable exact identity | Existing create/location/upload paths refuse a blind second POST/PUT. | Show ambiguous outcome; inspect exact reserved identity/path; no retry button. |
| Item identity journaled but no verified receipt | `file_journal_unverified` prevents re-upload. | At most offer read-only exact-item verification eligibility; existence, filename or size alone never proves success. |
| Status change remains `dispatched` | The existing recheck leaves `dispatched` status unchanged. It writes late-effect ledger data only for changes already `complete` or `needs_attention`. | Diagnosis only reports the stored state. Keep the existing effectful recheck separate; do not close while a sender may still run. |
| Lease remains live | A worker may still own the run. | Wait/re-inspect. Expiry alone is not proof a remote request stopped. |
| Missing/stale/digest-mismatched artifacts or unknown receipt | Existing checks refuse the step. | Block continuation; require a fresh lookup/new run when original pinned evidence is unavailable. |

### Readback-only file recovery candidate

**[PLANNED; feasibility unknown.]** First test this as a verifier, not a writer, with sanitized fixtures and then a disposable sandbox run after separate approval. The ordinary runner checks bundle freshness before it reaches the pending-file row; that freshness window is distinct from verifier integrity. A future verifier could inspect a stale saved bundle only through an explicitly stale-tolerant, integrity-only path (the existing `allowStale` boundary), while downloading source bytes afresh and checking the pinned metadata/hash. It must keep provenance checks (valid stored manifest/bundle and copy-policy digest matching the dispatch), then reread the destination by exact journaled item ID in the expected site, drive, parent and path. The existing exact-hash or package attestor must succeed; for XLSX/DOCX, retain the complete package-attestation receipt and exact digest. Missing/duplicate items, source drift, changed policy, failed attestation, unknown SharePoint deltas or missing provenance remain blocked. If artifact integrity cannot be established, stop. This verifier would establish evidence only: receipt writing alone cannot resume a run whose ordinary freshness precondition has expired. Under current code Request 1003308 remains blocked and the supported fallback is a new run; any freshness remedy that enables continuation needs its own reviewed contract, separate from the receipt transition.

If feasibility passes, a later proposal must define a fenced, typed receipt transition under the current run token/generation/version and compare-and-set against the current resource outcome, including the exact package-attested digest where applicable. It cannot change a dispatch marker, synthesize evidence, skip later files, or mark `ready`; the ordinary terminal `verify` step remains the only path to `ready`. Any concurrency, late-write, stale-worker or receipt mismatch must leave the run blocked. Do not use 1003308 as the first proof or mutation rehearsal.

## Additional operations and recommended order

1. **Read-only stopped-run explanation — shipped in #426.** The existing inspect response derives Basic-run guidance from ledger state, using the existing bundle freshness helper. It preserves superuser authentication and actor ownership, makes no write or remote read, and requires no migration. Unknown or unresolved dispatch evidence blocks Basic continuation; supported transient/no-dispatch cases retain retry. Other known recipes are not assessed and retain their existing controls after successful inspection; missing or failed inspection disables Advance until refreshed.
2. **Clear status-change outcomes — built and reviewed, awaiting release.** Improve explanation of the form's existing status recheck: it reports the current outcome and leaves dispatched changes dispatched; for already complete or needs_attention changes it can write newly observed late-effect ledger data. Keep this operation separate from read-only stopped-run diagnosis. Keep `--status-abandon` CLI-only while no web-safe proof establishes every sender has stopped, including suspended invocations. Recheck journals late payment/tracking/email effects only for changes already complete or `needs_attention`; keep duplicate-producing transitions blocked.
3. **Disposable readback-verifier proof.** Cover exact-hash and package paths, exact-ID lookup, source/item missing, duplicates, metadata/version/policy drift, incomplete receipts, ambiguous responses, concurrent claims, lease expiry and stale-worker fencing. This proof performs no write to a retained Production run. Only a separately accepted design can add a receipt-writing recovery operation.
4. **Separate higher-effect actions.** Keep status `--rerun`, cast creation/reviewer binding, and reviewer-slot PATCH as one operation per separately reviewed release. Each needs a target/effect preview, current actor/target/marker check, explicit confirmation, journal-before-dispatch, exact-ID ambiguity recovery and readback. Existing CLI support does not by itself authorize exposing the action through the form.
5. **Retirement as a separate plan.** Decide first whether operators need a display disposition, a terminal run state, or actual resource retirement. Inventory all status readers, constraints, CLI, artifacts/sweeps, privacy and references before changing schema. Retain tombstones and evidence; touch only individually proven run-owned resources and report residue. Age alone must never trigger cascade deletion. No retention change belongs to this plan.

Keep v2 actor-scoped initially. A cross-actor support console is a separate authority/privacy decision and is not a prerequisite to explain an actor's own stopped run. Do not add a generic force/reset/abandon action or a new `abandoned` state in the first slice.
