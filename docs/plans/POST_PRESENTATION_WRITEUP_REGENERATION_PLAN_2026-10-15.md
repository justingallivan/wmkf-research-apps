# Post-presentation writeup regeneration

**[OWNER APPROVED — source-built on `codex/writeup-regenerate`, 2026-10-15; reviewed and locally verified.]** Scope: Workbench → Staff Deliberations → step 4. Generate a fresh Word document from current governed inputs, including reviews submitted since the preceding generation. Preserve the preceding document as a separate superseded version; do not transfer its staff edits. This is not deployed and no production operations were performed.

## Owner review

1. **Approved cutoff:** allow post-visit drafting and **group review**, but refuse once the **Final Writeup row** reaches `FINAL` / leadership review. The Pre-Site row already reaches `FINAL` at the start of group review; that flag alone does not prohibit regeneration.
2. **Approved stage preservation:** post-visit drafting stays post-visit drafting; group review stays group review. A regenerated group-review document starts with fresh sign-offs; sign-offs on the preserved document remain historical and do not approve the replacement.
3. **Approved colleague notice:** during group review, send a fresh handoff notice pointing colleagues to the replacement using the existing durable email mechanism and existing program/recipient rules. Preserve previous sent receipts; safely retire pending notices for the replaced source. Reuse the current group-review email copy and settings; the email opens the Final tab, which resolves the current document.

4. **Rollout gate (owner, 2026-10-15):** first production release offers regeneration to superusers only (route `isRegenerationRolloutViewer`); the owner runs it once on a real request, then a second release opens it to lead PDs. The sandbox rehearsal tooling is parked on `codex/writeup-regenerate`; the feature continues on `claude/writeup-regenerate` from `270269f62`.

The file replacement/preservation and availability during both stages are owner decisions from 2026-10-15. No schema/migration or new route is proposed. Existing `wmkf_producer` and generation-key fields identify this operation; `wmkf_reopencycleid` remains reserved for reopen/correction history.

## Opus review reconciliation and owner choices

The read-only Opus review at `docs/audits/POST_PRESENTATION_WRITEUP_REGENERATION_OPUS_REVIEW_2026-10-15.md` identified implementation gaps. Owner approved the stage cutoff, stage preservation, fresh group-review signoffs and colleague notice on 2026-10-15. The accepted resolutions below govern the implementation:

1. **Preparation history:** keep preparation receipts immutable. Both request-detail and cycle-list projections treat a receipt tied to a superseded predecessor in the current source lineage as historical; it must not become `document_pointer_changed` or `Needs attention`. A group-review successor receives its own group-review checkpoint/milestone; the prior checkpoint remains on the old Final row.
2. **Operation identity/retry:** key a regeneration as a canonical hash of `{operation:'post-presentation-writeup-regeneration-v1', requestId, expectedPreSiteArtifactId, expectedFinalArtifactId|null, clientOperationId}`. Store a distinct producer (`request-workbench-regenerate`) on the successor; leave `wmkf_reopencycleid` empty. The input fingerprint remains the frozen input snapshot's fingerprint and is not part of this operation key. At initial claim, persist the rendering snapshot before model execution. A same-operation retry with a persisted proposal core resumes that frozen output even if live reviews changed. If a process failed before persisting a complete model output/run, same-ID recovery fails closed and requires a deliberate new UUID; it never repeats a potentially paid model call. The snapshot does not contain enough proposal narrative text to reconstruct that model input, so this is the chosen safe boundary.
3. **Email recovery:** replacement email intent is staged before activation against the expected old pair and successor operation. When delivery sees the old pair still current and the successor is generating/ready but not current, it releases the lease and waits; this wait expires through the existing `transition_not_committed` terminal state, which the store can reopen. If the source row is superseded or the operation is proven abandoned, terminalize the intent with that same reopenable reason. Once the replacement pair is current, the activation path calls the existing `deliverGroupReviewHandoff` hook. Reuse current group-review copy/settings; prior sent receipts remain history. A concurrently accepted old notice cannot be recalled and its Final-tab link resolves to current state.
4. **Old-file edits:** regeneration never consumes the old file bytes, so the SharePoint version observed at user confirmation is provenance only. Edits after confirmation are allowed and remain on the preserved old item. A retry keeps the same operation ID and frozen output, avoiding a second model call; explicitly starting a new operation uses a new UUID. UI text asks group reviewers to stop editing and explains that later edits remain on the previous version.
5. **Writer and route constraints:** extend the existing Pre-Site POST allowlist for an explicit `mode:'regenerate'` and the expected row IDs/client UUID; ordinary `{requestId}` remains unchanged and unknown keys fail closed. Update its exact-body test. Keep one registered `createDocument` call in `transition-service.js`; extract/share the create helper for ordinary Final claims and regeneration's prepared successor, and keep its REQUIRED actor policy. Express the Pre-Site writer actor policy as a three-way policy at its existing call. Update the writer-gate fixture and require explicit REQUIRED actor resolution for regeneration.
6. **History and timestamps:** history derives the old stage from a linked Final row's group-review checkpoint when present; otherwise it is post-visit drafting. A new group-review Final row gets a fresh `wmkf_groupreviewstartedat`, which is also the displayed start for the replacement review.
7. **Citation fixes:** the ordinary Draft-only guard is in `artifact-service.js` around lines 91–104; the leadership transition is in `transition-service.js` around lines 191 and 298–326 in the reviewed baseline.

The distinct producer, key shape, fail-closed pre-model retry behavior and preparation-lineage rule are application contracts defined by this implementation; they are not Dataverse option values or schema additions.

## Source-built implementation contract

The existing `POST /api/workbench/pre-site-visit` route accepts only `{requestId}` for ordinary generation or the exact regeneration body `{requestId, mode:'regenerate', expectedArtifactId, expectedFinalArtifactId?, clientOperationId}`. It requires a resolved staff actor and the existing literal-on explicit-actor schema readiness before generation, then rechecks lead-PD/superuser authority and the exact current pair at activation. A regeneration key includes the client UUID and both expected rows; an active competing UUID returns the active pending row (HTTP 202) without loading inputs or starting another model call. A same-UUID active claim returns pending; a completed same-UUID replay returns its committed successor. Failed or expired work without a persisted core/upload fails closed and tells the user to explicitly confirm a new operation. Work with a persisted core or verified upload resumes from the frozen snapshot and does not consult live narrative or prompt state.

Post-visit drafting replaces only the Pre-Site pointer; group review creates a new Pre-Site/Final pair and changes both pointers in one ETag-fenced changeset. Existing SharePoint files, snapshots, sign-offs, sent notices, and distribution history remain attached to their old rows. New group-review notices use the existing durable email ledger and explicit replacement/fresh-signoff copy. GET projects independently refreshed Pre-Site and Final state plus bounded previous-version links; pre-group-review file access remains lead-PD/PC/superuser scoped. The cycle-list lineage includes superseded predecessors only for matching immutable preparation receipts. No schema, migration, or API route was added. The source-built files are the implementations cited by the route, Atlas, and service catalog; hosted Dataverse/SharePoint race behavior remains unverified until an isolated authorized rehearsal.

## Reuse decision and accepted transaction

**[VERIFIED]** `pre-site-visit/reopen-service.js:234` rejects a Final pointer/downstream artifact. Its `successorPayload`, lease/claim checks and `activateSuccessor` preserve the old Review row/file, create a client-UUID-bound successor, then ETag-supersede the old row and move the pointer atomically. It requires the source still match the recorded handoff bytes, copies those bytes and lands in Draft; regeneration must instead tolerate legitimate edits since that handoff and preserve the current old file. Those product semantics must remain intact.

**[VERIFIED]** `pre-rp-brief/reopen-service.js:114` is the closer orchestration example: validate an exact current source and UUID, recognize exact retries, then delegate to the existing generator rather than duplicate render/upload logic. Its sent-brief superuser/reason/distribution rules are specific to that product. Its UI (`StaffDeliberationsTab.js:969–1058`) retains one operation UUID, treats 202 as pending, refreshes authoritative state, and fences post-await success/error/finally updates with sequence and request identity.

**[SOURCE-BUILT; NOT DEPLOYED]** Added a narrowly guarded regeneration mode to the existing Pre-Site POST/service, extending the route allowlist with `requestId`, `expectedArtifactId`, `expectedFinalArtifactId` when applicable, and `clientOperationId`. Exact payload discrimination must preserve ordinary `{requestId}` calls; unknown keys/modes fail closed. Do not repurpose the superuser reopen endpoint. Keep creates in the existing Pre-Site artifact writer and Final transition writer; extend their orchestration/activation seams, not the adapter bypass surface.

1. Resolve current request, complete registry lineage, actor and stage server-side. Require `canChangeDraftWriteup` (lead PD or superuser), a resolved actor, and applicable schema readiness. Coordinators retain view-only access. Return the same eligibility/blocked reason in GET for the menu. Recheck authorization and the exact stage/pointer pair before activation; client-supplied state never grants permission. Unknown, inconsistent, leadership, Board Ready, Superseded, or missing-current states refuse.
2. Bind one operation UUID durably to the source using a distinct `wmkf_producer`, existing `wmkf_SourceDocument`, `wmkf_sourceversionid`, `wmkf_sourcecontenthash` and generation key. Use existing actor policy `REQUIRED` for this explicit action; do not write immutable origin fields directly. Do not invent a reopen reason or pretend this is an accidental handoff. Keep legacy reason-bearing reopen history separate. Explicitly distinguish regeneration in the correction DTO, pending projection and `correctionInProgress` calculation so its UUID cannot turn on correction-draft UI. The discriminator and operation key are application contracts defined in `shared/config/requestDocument.js` and `artifact-model.js`, not new schema identifiers.
3. On first claim, load current governed data and freeze its input snapshot. A retry first finds the same durable operation and resumes its frozen inputs/run/upload; it must not silently generate another row because reviews changed during a timeout. A deliberately new operation gets a new UUID and fresh inputs. Bind source, stage and operation identity before any model call. Keep the existing Executor/LLM seam.
4. Upload and verify a **new** SharePoint item; never overwrite or delete the old item. Keep the old pointer(s), Ready state and Word link usable throughout generation. Verify target identity/hash/version and reread source metadata before activation. Edits to the old file are non-blocking and remain in that preserved file; they are never copied into the replacement. SharePoint coauthoring cannot be transactionally locked with Dataverse: late edits remain in the preserved old file, and the dialog must make this clear.
5. **Post-visit drafting:** atomically mark the exact old Pre-Site row Superseded, activate the successor Ready/Review and move `wmkf_CurrentPreSiteVisit`. Record a milestone for the successor's own verified bytes/time/actor; never attach the old file's milestone version to the new item. Preserve the original milestone on the old row. No Final pointer is created.
6. **Group review:** prepare a new Pre-Site row and a new Final row sharing the new item. In **one** ETag-fenced changeset, supersede both old rows, activate successor Pre-Site Ready/Final and successor Final Ready/Review, bind Final→new Pre-Site, and move **both** current pointers. The new Pre-Site source link retains the old Pre-Site lineage; the old Final remains linked to its old source. Use the existing Final writer to prepare the successor without invoking ordinary handoff activation as a second transaction. Record a new group-review checkpoint for this replacement; keep the original checkpoint on the old Final. `committedFinal` must accept the new pair without weakening its same-item invariant.
7. Confirm committed state by exact readback before reporting success. Return current/pending and operation outcome; a lost response must recover the exact committed successor, not recreate it or reactivate a superseded result. Failures leave the old link live. Failed/expired attempts remain inspectable and retryable where safe; orphan cleanup only targets an exact unactivated successor identity after proving no current pointer references it. Never queue the preserved source file for cleanup.

## Races, history and downstream facts

**[SOURCE-BUILT; NOT DEPLOYED]** Reuse claim tokens, the existing 15-minute lease and alternate-key conflict handling. A live competing operation returns pending/conflict. Two distinct UUIDs may race the initial read; a preflight lease check alone does not serialize them. Source/request ETags and expected pointer/stage checks must ensure at most one activates; the loser cannot adopt the winner as its new source. Reclaim expired claims conditionally and fence stale workers before every write/upload/finalize. Test concurrent claim creation as well as concurrent activation.

A regeneration racing group handoff or leadership advancement loses if that transition changes the captured stage/row/pointer first. Conversely, transition attempts against a superseded source must fail. Suppress the same-tab group handoff while regeneration is observed pending. The separate Final tab and other sessions rely on server stage/ETag fences; no cross-tab coordination is claimed. Never reread and accept a newer ETag as permission to change the originally confirmed stage.
