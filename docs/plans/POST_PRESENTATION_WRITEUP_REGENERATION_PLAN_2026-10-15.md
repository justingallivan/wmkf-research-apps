# Post-presentation writeup regeneration

**[PLANNED — owner review required; no implementation authorized yet.]** Scope: Workbench → Staff Deliberations → step 4. Generate a fresh Word document from current governed inputs, including reviews submitted since the preceding generation. Preserve the preceding document as a separate superseded version; do not transfer its staff edits. Stay in `/Users/gallivan/Code/WMKF_Apps-writeup-regen`, branch `codex/writeup-regenerate`; no main push or production operations.

## Owner review

1. **Confirm the cutoff:** allow post-visit drafting and **group review**, but refuse once the **Final Writeup row** reaches `FINAL` / leadership review. The Pre-Site row already reaches `FINAL` at the start of group review; that flag alone must not prohibit regeneration.
2. **Proposed stage preservation:** post-visit drafting stays post-visit drafting; group review stays group review. A regenerated group-review document starts with fresh sign-offs; sign-offs on the preserved document remain historical and do not approve the replacement.
3. **Proposed colleague notice:** during group review, send a fresh handoff notice pointing colleagues to the replacement using the existing durable email mechanism and existing program/recipient rules. Preserve previous sent receipts; safely retire pending notices for the replaced source. Approval of this plan must settle this behavior before implementation; no messages are sent during planning.

The file replacement/preservation and availability during both stages are owner decisions from 2026-10-15. Items 1–3 make the boundary and its consequences explicit for approval. No schema/migration or new route is proposed. If existing fields cannot express the audited operation without changing their meaning, return with a named schema proposal before building that part.

## Reuse decision and proposed transaction

**[VERIFIED]** `pre-site-visit/reopen-service.js:234` rejects a Final pointer/downstream artifact. Its `successorPayload`, lease/claim checks and `activateSuccessor` preserve the old Review row/file, create a client-UUID-bound successor, then ETag-supersede the old row and move the pointer atomically. It requires the source still match the recorded handoff bytes, copies those bytes and lands in Draft; regeneration must instead tolerate legitimate edits since that handoff and preserve the current old file. Those product semantics must remain intact.

**[VERIFIED]** `pre-rp-brief/reopen-service.js:114` is the closer orchestration example: validate an exact current source and UUID, recognize exact retries, then delegate to the existing generator rather than duplicate render/upload logic. Its sent-brief superuser/reason/distribution rules are specific to that product. Its UI (`StaffDeliberationsTab.js:969–1058`) retains one operation UUID, treats 202 as pending, refreshes authoritative state, and fences post-await success/error/finally updates with sequence and request identity.

**[PLANNED]** Add a narrowly guarded regeneration mode to the existing Pre-Site POST/service, using existing request fields `requestId`, `expectedArtifactId`, `expectedFinalArtifactId` when applicable, and `clientOperationId`. Exact payload discrimination must preserve ordinary `{requestId}` calls; unknown keys/modes fail closed. Do not repurpose the superuser reopen endpoint. Keep creates in the existing Pre-Site artifact writer and Final transition writer; extend their orchestration/activation seams, not the adapter bypass surface.

1. Resolve current request, complete registry lineage, actor and stage server-side. Require `canChangeDraftWriteup` (lead PD or superuser), a resolved actor, and applicable schema readiness. Coordinators retain view-only access. Return the same eligibility/blocked reason in GET for the menu. Recheck authorization and the exact stage/pointer pair before activation; client-supplied state never grants permission. Unknown, inconsistent, leadership, Board Ready, Superseded, or missing-current states refuse.
2. Bind one operation UUID durably to the source using existing `wmkf_reopencycleid`, `wmkf_SourceDocument`, `wmkf_sourceversionid`, `wmkf_sourcecontenthash` and generation key. Use existing actor policy `REQUIRED` for this explicit action; do not write immutable origin fields directly. Do not invent a reopen reason or pretend this is an accidental handoff. Keep legacy reason-bearing reopen history separate. Explicitly distinguish regeneration in the correction DTO, pending projection and `correctionInProgress` calculation so its UUID cannot turn on correction-draft UI. Define/test the regeneration discriminator and key format before coding; these are proposed application contracts, not existing identifiers.
3. On first claim, load current governed data and freeze its input snapshot. A retry first finds the same durable operation and resumes its frozen inputs/run/upload; it must not silently generate another row because reviews changed during a timeout. A deliberately new operation gets a new UUID and fresh inputs. Bind source, stage and operation identity before any model call. Keep the existing Executor/LLM seam.
4. Upload and verify a **new** SharePoint item; never overwrite or delete the old item. Keep the old pointer(s), Ready state and Word link usable throughout generation. Verify target identity/hash/version and reread source metadata before activation. A detected source edit requires refresh/reconfirmation, not silently replacing newly edited work. SharePoint coauthoring cannot be transactionally locked with Dataverse: late edits remain in the preserved old file, and the dialog must make this clear.
5. **Post-visit drafting:** atomically mark the exact old Pre-Site row Superseded, activate the successor Ready/Review and move `wmkf_CurrentPreSiteVisit`. Record a milestone for the successor's own verified bytes/time/actor; never attach the old file's milestone version to the new item. Preserve the original milestone on the old row. No Final pointer is created.
6. **Group review:** prepare a new Pre-Site row and a new Final row sharing the new item. In **one** ETag-fenced changeset, supersede both old rows, activate successor Pre-Site Ready/Final and successor Final Ready/Review, bind Final→new Pre-Site, and move **both** current pointers. The new Pre-Site source link retains the old Pre-Site lineage; the old Final remains linked to its old source. Use the existing Final writer to prepare the successor without invoking ordinary handoff activation as a second transaction. Record a new group-review checkpoint for this replacement; keep the original checkpoint on the old Final. `committedFinal` must accept the new pair without weakening its same-item invariant.
7. Confirm committed state by exact readback before reporting success. Return current/pending and operation outcome; a lost response must recover the exact committed successor, not recreate it or reactivate a superseded result. Failures leave the old link live. Failed/expired attempts remain inspectable and retryable where safe; orphan cleanup only targets an exact unactivated successor identity after proving no current pointer references it. Never queue the preserved source file for cleanup.

## Races, history and downstream facts

**[PLANNED]** Reuse claim tokens, the existing 15-minute lease and alternate-key conflict handling. A live competing operation returns pending/conflict. Two distinct UUIDs may race the initial read; a preflight lease check alone does not serialize them. Source/request ETags and expected pointer/stage checks must ensure at most one activates; the loser cannot adopt the winner as its new source. Reclaim expired claims conditionally and fence stale workers before every write/upload/finalize. Test concurrent claim creation as well as concurrent activation.

A regeneration racing group handoff or leadership advancement loses if that transition changes the captured stage/row/pointer first. Conversely, transition attempts against a superseded source must fail. Keep UI transition actions disabled while regeneration is observed pending, but rely on server fences for other tabs/sessions. Never reread and accept a newer ETag as permission to change the originally confirmed stage.
