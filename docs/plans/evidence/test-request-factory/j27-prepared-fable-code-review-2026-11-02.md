# Prepared J27 Factory — Fable code review

Owner authorized source disclosure and possible subscription usage. OAuth-only host CLI; environment whitelist, Read/Grep/Glob, safe mode, empty MCP configuration. Model: claude-fable-5-1. No permission denials. First verdict NEEDS CHANGES; correction review pending. No live writes.

**Verdict: NEEDS CHANGES.** The prepared-fixture discriminator, create body, fences, journal CAS and old-manifest compatibility are correct in source. Three P1 items block a safe owner run: a freshness fence that makes finalization impossible after six hours or after any edit to the real source, a one-row journal with no recovery from a 412 or a post-write effects flag, and a fingerprint change that disables every Factory mode on the managed ledgers until 094 is applied. No P0.

## Whole-flow trace against source

- **Discriminator is explicit and body-bound.** `buildCloneManifest` adds `preparedFixture` only for production plus a J27-or-later cycle (`basic-clone-steps.js:723`); `compileBody` refuses any other value, a pre-27 cycle or a missing director (`:639-640`); the compiler emits readiness false and omits Request Status only on the exact string with status undefined, and blocks any other combination (`policy.js:297-303`). The fence step recompiles from `manifest.values` (`run-runner.js:561-563`), so a manifest reserved before this change has no key and recompiles byte-identically. The unit test at `test-request-production-target.test.js:530-543` proves that. Old manifests cannot finalize: `assertPreparedFixtureContract` requires the key, readiness false in the body, no status key and matching hashes on both manifest and run row (`prepared-fixture-contract.js:14-20`).
- **No direct Request Status write, false readiness at create.** The POST fence refuses a body carrying readiness unless it is false with no status key (`production-write-fence.js:390`). Readback tolerates an absent body status (`sandbox-clone.js:164-166`). Clone verification keeps the null Phase II check and adds a refusal if the clone reads back ready (`basic-clone-steps.js:1491-1492`).
- **Basic clone otherwise unchanged.** Only the readback projection and the production metadata preflight grow by the readiness column. Sandbox and old production runs take the same code path.
- **Phase I then Phase II.** The finalizer requires Invited, Pending Committee Review and Phase II Pending live (`readiness-finalizer.js:16`), and the transition table still forces Phase I first.
- **Owner CLI, true-only, journaled.** Preview returns before any interlock or journal write (`:55`). The planned-to-dispatched CAS selects one sender (`readiness-journal.js:20`); the fence admits exactly one boolean true on the destination path with a concrete If-Match and refuses anything naming the source (`production-write-fence.js:400-412`). The pg test proves one winner of two concurrent dispatches and terminal complete. Effects keys all pass both receipt grammars (`run-ledger.js:158-166`, `054:39-67`).
- **Ambiguous writes.** A thrown PATCH leaves the row dispatched and the rerun reads before deciding; a landed write recovers, a non-landed one never resends (`:71`, `:79`). Correct.
- **Isolation, metadata, interlock, observation.** Marker and run identity, cycle link, Foundation baseline, SharePoint identity, file re-verification and Boolean update-ability are all re-read (`:25-45`); the interlock preflight runs before the plan row (`:56`); jobs and census are observed after the write with Phase II Pending required (`:83-88`).
- **Copy.** Intake and run panel now separate clone completion from staff readiness.

## Findings

**P1-1. Finalization re-runs the pre-create source fence, so it is impossible after six hours or after any edit to the real source.** `readiness-finalizer.js:46` calls `fenceSource`, which calls `bundleSourceOf(manifest)` with the default `allowStale=false` (`basic-clone-steps.js:969`) and then `assertBundleFresh` (`bundle-file-copy.js:100-107`, six-hour limit), and also requires the live source revision to equal the export revision (`:974-978`). Failing scenario: export at 09:00, clone and both phase changes by 12:00, owner inspects the uncharacterized Invited effects and runs `--finalize-readiness --confirm` the next morning. Result: "Source bundle is older than 6 hours", permanently, because the run is ready and bound to that bundle hash and no re-prepare is possible. The same happens the moment staff touch the real D26 source after export. The unit test mocks `fenceSource` (`test-request-readiness-finalizer.test.js:10`), so neither path is exercised. Minimal correction: replace line 46 with `bundleSourceOf(manifest, { allowStale: true })` plus the pure `assertCopiedSourceValues(source, manifest.createBody)`. The bundle is already hash-bound to the run row at line 23, and the Factory's own non-writing of the source is guaranteed by the fence clients, not by a live revision read.

**P1-2. The one-row journal has no recovery path, so an ordinary 412 or a post-write effects flag strands the fixture.** The ETag is captured at the top of `prerequisites` (`:26`), then roughly ten GETs and a full download of every copied file (`reverifyClone`, proposals of 5 to 19 MB per the inventory) run before the PATCH at `:70`. Any row touch in that window returns 412, which `:72-75` records as `needs_attention`, and `:54` then refuses forever; the primary key is `run_id` (`094:4`), so no second intent can exist. Failing scenario: a late async job updates the Request during the file re-download, the PATCH gets 412 with nothing written, readiness stays false, and the fixture can never be finalized without manual SQL. A second case: `:86-87` flags `readiness_unexpected_effects` after readiness is already true, so the fixture is live in My Proposals while the journal is terminal with no completion path. A third: a PATCH that throws and never lands leaves `dispatched` with no abandon, unlike the status setter (`rehearse-test-request-sandbox.mjs:1243-1271`). Minimal correction: re-read the ETag immediately before `journal.plan` rather than at the top of `prerequisites`; treat 412 distinctly, as the status runner does (`status-change-runner.js:144-147`); and add an owner-confirmed, ledger-only reset that moves `needs_attention` or `dispatched` back to `planned` with a fresh `etag_before` only when the live row reads readiness false, on the status-abandon checklist precedent.

**P1-3. The tracked fingerprint now includes 094, which refuses every Factory mode on both managed ledgers until the migration is applied.** `compareLedgerFingerprint` reports a tracked table absent live as `missing`, and `ledger-guard.js:143-145` throws for every mode but `ledger-check`. The approved-ahead list covers the opposite direction only (live ahead of checkout). Failing scenario: this branch is merged and deployed before `ledger:apply`; the admin form's Confirm (`admin-run-service.js:706`), `--advance`, `--set-status`, `--run-recheck` and `--run-inspect` all refuse on `ledger_prod` and `ledger`. The atlas note at `docs/atlas/postgres-test-request-runs.md:389-391` acknowledges this, but the plan framed the migration as a prerequisite for finalization only. This is a release-sequencing blocker, not a code defect: apply 094 to both managed ledgers in the same owner-authorized step as the merge, or hold the merge until then.

**P2-1. A stale status-change row blocks finalization even when live state is correct.** `readiness-finalizer.js:31` requires every change to be `complete`. The status journal allows several changes per run, so a Phase I attempt that went `needs_attention` on a 412 (nothing written) followed by a successful retry leaves a correct live pair and a complete row with the digest, yet finalization refuses forever. There is no writer that reopens or clears a change (`run-ledger.js:1285-1306`). Correction: gate on no open change (planned, dispatched, applied) plus at least one complete change whose digest is Phase II Pending, which is the live-state-corroborated gate the plan review asked for.

**P2-2. An incomplete package at Confirm surfaces as a 500.** `assertPreparedPackage` throws a plain `Error` inside `buildCloneManifest` (`basic-clone-steps.js:732`), which `admin-run-service.js:666` does not wrap in `refuse`. The two J27 test sources in the inventory lack a bibliography, so an admin choosing one learns nothing until an unexplained server error at Confirm. Nothing is left behind, since the Blob writes come later. Correction: wrap with a 409 `refuse` and check the package at preview.

**P2-3. Three full prerequisite passes per confirmed run.** `prerequisites` runs at `:51`, `:78` and `:89`, each re-downloading and hashing every copied file. Run the heavy file re-verification once before the plan row and limit the post-write re-reads to identity, pair, status and readiness.

**P2-4. Operator discoverability.** The `--help` text (`rehearse-test-request-sandbox.mjs:452-472`) has no line for `--finalize-readiness`, its read ack or its confirm ack. The runbook does cover it.

**P2-5. Sandbox readback column.** `READBACK_FIELDS` is used for every target (`basic-clone-steps.js:282`) and now selects `wmkf_readyforreview`. Production has the column (readiness metadata evidence file). I could not verify the sandbox has it; if it does not, every sandbox rehearsal readback fails with a 400. Confirm before the next sandbox run.

## Prerequisites verified and verdict

Verified from source and evidence: readiness Boolean createable and updateable in Production; all six Research J27 requests unready; six invited D26 sources carry all seven documents; the migration depends only on 054's receipt function; the journal pg test runs every ledger migration file; the fingerprint JSON matches the 094 DDL; preview mode performs no journal or Dataverse writes; the interlock preflight precedes the plan row. Not verified: sandbox readiness column (P2-5); the live reaction to the readiness PATCH, which the finalizer observes rather than assumes.

Verdict: **NEEDS CHANGES.** Fix P1-1 and P1-2 in code, then coordinate P1-3 as a release step. The migration remains unapplied to managed ledgers and no Production write or deployment is authorized by this review.
