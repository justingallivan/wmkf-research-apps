### 3.1 Stage A resolve — PIs, read-only

For each in-scope award: read `_wmkf_projectleader_value`, `_akoya_applicantid_value`, and the junction rows with role PI. Classify:

- `write` — exactly one PI junction row, its contact equals the project leader, applicant account present, column empty.
- `already-set` — column already holds a value (never overwrite).
- `no-junction-row` — the project leader has no PI junction row. The junction backfill (`scripts/backfill-request-person-junction.js`) predates later requests, and Connor's dual-write flows have not shipped (Atlas), so these are expected for newer awards. Creating the row is a separate owner decision; report the count.
- `pi-mismatch` — junction PI contact differs from the project leader. Review.
- `no-applicant` — no applicant account. Review.
- `multiple-pi-rows` — more than one PI junction row on the request (the alternate key allows it when the contacts differ). Review.
- `other` — any state the classes above miss; never written.
- On `write` rows, `contact_account` compares the PI contact's current parent account with the applicant: `same`, `elsewhere`, `empty` or `not-account`. `elsewhere` rows are still written (the applicant is the award-time institution) but listed so the owner can see who moved or is mislinked.

**Built 2026-10-20:** `scripts/backfill-research-pi-institution-at-award.mjs` with `--resolve`, `--apply`, `--verify` and `--rollback`; decision rules in `scripts/lib/research-iaa-backfill.mjs`, tested by `tests/unit/research-iaa-backfill.test.js`. Apply needs `--confirm=<resolve hash>` and `--approver`. Before each write it re-reads the request and its PI rows and skips any drift from the resolve snapshot (status, program, meeting date, applicant, project leader, PI row count/identity). Contact targets also re-collect the contact's in-scope awards, re-run the latest-award selection, and re-run the duplicate search. It then re-reads the target and writes only an empty value with `If-Match`, taking the rollback ETag from the PATCH response itself (`Prefer: return=representation`), so no separate read can attribute another writer's version to this run. `--contact-accounts` adds the second group: contacts with no account and no duplicate, using the applicant of the contact's latest in-scope award whether or not that award's Institution at Award is already set; a same-date tie between different applicants is not written. Rollback clears only attributed writes whose ETag and value are unchanged; failed rollback attempts stay retryable and under verify, and cleared targets are never re-applied. Rules as built: [DERIVED-FROM: §3.2 approved co-PI list; independent of TBD count]

- Contact match: one contact holding the email in any of the three fields; else one contact with the same name (first name or initial) and a related email domain (equal, or one a subdomain of the other; free-mail domains never count). Anyone else with the same name, or with the same last name at the same domain or account (nicknames), sends the row to review (`possible-existing-contact`) rather than proposing a new contact. A capped last-name search does the same, and so does a name without both a first and a last part (`name-unparseable`). Last names compare on the final word and final hyphen segment ("Smith Jones" ~ "Smith-Jones"). The last-name query fetches every stored last name ending in the compared surname (so "O'Connor" and "Smith-Jones" are found) and sends the accent-stripped form ("nunez"), so finding a contact stored as "Núñez" relies on Dataverse comparing strings accent-insensitively [ASSUMED; not probed — the sandbox run had no such pair]; if it does not, that person can land in `new-contact`, which the owner sees in the workbook.
- Institution at Award, extracted: every signal that fires must agree — the applicant when the proposal email's domain matches the PI's; the domain map's clear winner; a unique exact Account name/AKA/legal-name match on the stated institution (`lib/utils/reviewer-institution-account-match.js`). Disagreement is `conflicting-evidence`; none is `no-account-match`; an `assumed` institution is `assumed-institution`. Recorded: the contact's account, else the applicant on a PI email-domain match, else the domain map.
- Domain map: accounts of active contacts whose primary email has the domain; a winner needs at least `--map-min` (default 3) contacts and `--map-share` (default 0.9) on one account. A domain over the 5,000-row read cap has no winner (`capped`; the read is a prefix, not a sample). Each row's domain counts go into the JSONL and the workbook.
- Blocking classes, in order: `out-of-scope`, `keck-applicant`, `applicant-not-account`, `ambiguous-contact`, `possible-existing-contact`, `is-pi` (the contact is the project leader or has a PI row), `inactive-contact`, `already-set`, the Institution at Award classes above, and `duplicate-contact` (the Stage A duplicate search, only where a new junction row would attach to the contact). Other rows are `ready` with actions: `create-contact`, `link-proposed-contact`, `suggest-contact-account`, `create-junction-row`, `set-iaa`.
- New contacts across the batch: one person on several awards gets one proposed contact. Rows with the same email form a group, whose first row carries `create-contact` and the others `link-proposed-contact` (JSONL `proposedContactRef`). People who share no email but have the same name, or the same last name at a related email domain or the same resolved Institution at Award (nicknames), send every group they touch to review (`possible-same-new-person`). The web search runs once per group.
- Contact accounts are contact-level rows (`con|<contactId>`, action `set-contact-account`, with the winning award recorded), separate from the award rows, so the proposal stands whether or not the winning award needs an Institution at Award write. An existing empty-account contact (not a duplicate, active) gets the institution of their latest in-scope award across every award they are on (co-PI rows whether or not their Institution at Award needs writing, and their PI rows); a latest award whose institution is unresolved, or same-date awards at different accounts, selects nothing. A new contact gets only a *suggested* account from the web search, confirmed in its own workbook column (`suggest-contact-account`): result titles must name the person and not read as an event, news item or former role, hosts like LinkedIn or journals are ignored, the host must map to an account through the domain map, and all counted results must agree. Searches are cached in the output folder (the cache holds names), so a rerun spends nothing for the same query.
- Outputs: `research-copi-iaa-resolve.jsonl` (ids only: extracted rows are keyed by a 16-character hash of request number + normalized name; a meta line holds input file hashes and settings), `research-copi-iaa-review.xlsx` (names; Confirm? = Yes/No/Unsure, hidden key column), and the resolve hash.
