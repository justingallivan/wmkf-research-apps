## Why

The scheduled-email engine sends the grantee materials reminder (`grantee_abstract_reminder`, the only workflow the status table allows [VERIFIED via `lib/db/migrations/036_scheduled_email_messages.sql:56-57`, mirrored at `scripts/setup-database.js:891-892`; no later migration alters it]) for every program. It has hazards that do not depend on the Liaison change: it can send the same email twice once a send has been requested, it can adopt a stale draft, and it can drop a PD's edit (*Current engine facts*). Part A fixes these.

The Research Liaison switch gives **new** reminders the current Liaison. A row already queued keeps the recipients it was created with (liaison plan, owner answer 9). The point-in-time measurement found no queued rows, so the remaining prospective case is a Liaison change while a row waits to send. Part B covers it, reusing Part A's recipient generation.

## Current engine facts

All line numbers are as of `ed04b6c17`.

- The daily cron runs four passes in order: process deliverables (create or PD-handoff rebuild), send digests, deliver due messages, then finalize sent rows whose source update did not complete [VERIFIED via `lib/services/cron/grantee-deliverable-reminders-service.js:199-251`].

The row stays `sending` until its lease expires. The due query includes `sending` rows with an expired lease [VERIFIED via `lib/services/scheduled-email-store.js:81-92`]. On the next claim, an activity that is not yet accepted gets `recordSendRequested` (a COALESCE no-op) and **another `sendEmail`** [VERIFIED via `scheduled-email-service.js:363-377`]. Only the test-Request path refuses to resend [VERIFIED via `scheduled-email-service.js:243-275`].
- **A failed activity read looks like no activity.** Reading a stored `dynamics_email_id` uses `.catch(() => null)` at `scheduled-email-service.js:118` and `:320` [VERIFIED]. A transient read error then falls through to correlation recovery or a new activity create (`:108-138`). The persist fence (`dynamics_email_id IS NULL OR = new id`, `scheduled-email-store.js:221-231`) stops a second id from being recorded, so the row fails with "could not be persisted" or "Multiple … share correlation" and leaves an orphan draft [VERIFIED by reading the path; not reproduced].

The send path reuses an existing activity as created and renders a body only when none exists [VERIFIED via `scheduled-email-service.js:319-359`]. A PD who edits a `failed` row that already has an activity sees the edit saved, but the older content is what is sent.
- **The PD-handoff rebuild can adopt the old draft.** `reassignScheduledEmail` rewrites recipients, content and posture when the stored PD differs, the row is `scheduled`/`failed`, both transport fields are null and no lease is live. It has no expected-version predicate [VERIFIED via `scheduled-email-store.js:344-377`]. A crash between activity create and persist leaves a Dynamics draft under correlation key `wmkf-scheduled-recipient:<id>` with `dynamics_email_id` still null [VERIFIED via `scheduled-email-service.js:76-78,122-135`]. The rebuild keeps the same row id, so the next send recovers that old draft by the same key (`:118-120`) and sends the former PD's recipients and content.
- `cancelScheduledEmailForSource` checks only id and status (`scheduled`/`failed`/`sending`) and clears any lease, including another worker's [VERIFIED via `scheduled-email-store.js:173-188`].
- The digest groups `scheduled`/`failed` rows into approval-pending or upcoming and unreceipted `sent` rows into FYI [VERIFIED via `scheduled-email-store.js:305-313`; `scheduled-email-service.js:414-437`]. Approval-pending rows repeat in every digest until actioned and need no receipt; only FYI ids are frozen into a digest run [VERIFIED via `scheduled-email-service.js:455-466`].

## Part A: engine hardening (every program)

A1. **Send intent is the point of no return.** `send_requested_at IS NOT NULL` is the durable no-resend predicate; `last_error_code` is never used to decide whether transport may be called. Once send intent is set, the ordinary path reconciles only, as the test-Request path does today: accepted → record sent and finalize; otherwise → no `sendEmail`, and the row is marked unconfirmed (A2). This applies to send-now as well as the cron.

A2. **Unconfirmed is an error code, not a new status** (owner decision A-1, S551: error code; it needs no status CHECK migration). The row is set to `failed` with `last_error_code = 'scheduled_email_send_unconfirmed'`, and the lease is released.
- This happens **immediately**, in the `uncertain` branch that today skips `recordFailure` (`scheduled-email-service.js:384-392`), so the row does not sit in `sending` with a live lease, invisible to the digest query, until the next claim.
- One shared helper, `isSendUnconfirmed(row)`, is the only display/guard test for this state. Every reader of `failed` rows uses it (the digest grouping, the UI, the edit/approve/send-now guards and the due-send path), and each has a test. The transport guard remains the independent `send_requested_at` predicate, so a missing or temporarily cleared display marker cannot permit a resend.
- The due query keeps claiming it, but only for reconciliation (A1), so a late acceptance is recorded and finalized without anyone acting.
- `claimScheduledEmailSend` currently clears `last_error_code` and increments `attempt_count` on every claim [VERIFIED via `scheduled-email-store.js:190-219`]. Change its update to preserve or re-stamp `scheduled_email_send_unconfirmed` whenever `send_requested_at IS NOT NULL`; an unaccepted reconciliation releases the lease with the same marker still durable. `attempt_count` means ordinary delivery claims begun before send intent, not transport API calls: use `attempt_count = attempt_count + CASE WHEN send_requested_at IS NULL THEN 1 ELSE 0 END`. Reconciliation claims never increment it. The stopped-row pass takes no claim and never changes it.
- The digest lists it in a new **Needs attention** section, never under upcoming. Like approval-pending, the section repeats every day until the row is resolved, so no receipt or frozen membership is needed (this replaces revision 0's open requirement 3).
- The UI shows "Send status is uncertain. Check the email history before trying again" (`EMAIL_SEND_OUTCOME_COPY.uncertain`) and offers only Stop. Edit, approve and send-now are refused for these rows.
- **Late acceptance after a stop** (owner decision A-2, S551: check). Stop can end a row that Dynamics is still processing; so can the source-eligibility cancel at `scheduled-email-service.js:315`, which runs after the claim even when a send was requested. A daily cron pass reconciles every row with `status = 'stopped'`, `send_requested_at` set and `stopped_at` within the last 7 days, whoever stopped it. It reads the activity and never calls `sendEmail`. If Dynamics accepted it, a new store write moves the row from `stopped` to `sent`, fenced on those same columns (`recordScheduledEmailSent` needs a lease the stopped row does not have), and then finalizes it. The deliverable is marked Reminder sent, and the row appears in the PD's sent FYI. The rule: stopped wins unless Dynamics proves the email went. Every row with send intent has a `dynamics_email_id` [VERIFIED via `scheduled-email-store.js:234-245`]. Nothing here needs a migration.

A3. **A failed read of a stored activity is never absence by default.** When `dynamics_email_id` is set, a timeout, network error or 5xx ends the attempt as a retryable failure; if send intent exists, A2's unconfirmed marker is preserved. There is no correlation recovery and no create. Correlation recovery runs only when `dynamics_email_id` is null.
- Classification uses the HTTP status the read error carries (`error.status` [VERIFIED via `lib/utils/service-error.js:37-41`]; `getRecord` throws on every non-OK response and does not retry [VERIFIED via `lib/services/dynamics/read-ops.js:129-132`]). A 404 is definitive missing and a 403 is definitive forbidden. Everything else, including 401 (a token problem, not a property of the row), 408, 429, 5xx and a network error, is transient. Store distinct `scheduled_email_activity_missing` and `scheduled_email_activity_forbidden` error codes, release the lease, exclude those codes from automatic due claims and upcoming, and list them under **Needs attention**.
- One shared helper, `scheduledEmailAttentionReason(row)`, returns `unconfirmed` (via `isSendUnconfirmed`), `activity_missing`, `activity_forbidden` or null, and every digest, UI and guard reader uses it. The due query's SQL exclusion of the two definitive codes is the one place that cannot call it, so a parity test pins the SQL predicate to the helper.
- Manual recovery is explicit: staff check Dynamics and email history, send by hand if appropriate, then Stop the scheduled row. The engine does not clear the stored activity id, create a replacement, or keep retrying a definitive state. Any manual source-record follow-up remains outside this automation.

A4. **No edits after the activity exists.** `updateScheduledEmailDraft` and `approveScheduledEmail` add `dynamics_email_id IS NULL AND send_requested_at IS NULL`. The UI disables editing on those rows and gives the reason. A PD who needs to change a row that is stuck after activity creation stops it and sends by hand.

A5. **Recipient generation for the PD-handoff rebuild.**
- New column `recipient_generation INTEGER NOT NULL DEFAULT 0`: a migration, migration-manifest entry, `scripts/setup-database.js` mirror and Atlas update.
- The correlation key is `wmkf-scheduled-recipient:<id>` at generation 0 (unchanged, so existing rows keep recovering) and `…:<id>:g<n>` after that. Every create and recovery uses the row's current generation, so an older generation's draft is never adopted.
- `reassignScheduledEmail` is one atomic reset. It accepts `scheduled` or `failed` rows and also `sending` rows whose lease is expired, but only when `dynamics_email_id IS NULL`, `send_requested_at IS NULL`, the PD differs, `version = expectedVersion`, and no lease is live. In the same update it writes the new PD/draft/posture, sets `status = 'scheduled'`, clears `lease_token` and `locked_until`, increments `recipient_generation` and `version`, and clears the former review/approval/error fields. `attempt_count` is retained as claim history. The next delivery must take a fresh claim.
- The cron passes the version of the row it just read; a wrong version or live lease is a no-op reported as deferred, as it is today.
- An older-generation draft left in Dynamics is an unsent draft. The cron summary counts rebuilt rows. A read-only probe that lists drafts by correlation key is the cleanup report; deleting drafts is a separate, owner-authorized step.

A6. **Fenced source cancel.** The two `cancelForSource` calls inside `deliverScheduledEmail` (`scheduled-email-service.js:315,363`) require the caller's `lease_token`. The pre-claim test-Request stop (`:305`) requires no live lease.

## Part B: re-address on a Liaison change (after Part A)

B1. **Where.** In `deliverScheduledEmail`, after a successful claim and before any activity lookup, only when `dynamics_email_id` and `send_requested_at` are both null. The Liaison is resolved with `resolveRequestLiaison` plus a contact read, the same as row creation. For this workflow, creation and re-address writes keep `recipient_contact_ids` in `[PI, Liaison?]` order so the stored Liaison contact id is an explicit part of the comparison.

B2. **What.** Recipient drift means either the Liaison contact id changed or its trimmed, lowercased email changed, including a Liaison/Cc gained or dropped. The contact-id comparison is independent of the email comparison, so the same address on a different contact still drifts. Before writing, recompute `approval_required` from review-all plus the current recipient contact ids.

B3. **One transition, including posture.** `readdressScheduledEmail` is fenced on lease token, expected version, `sending` status and both transport fields null. In that same update it writes Cc and the ordered recipient contact ids, persists the recomputed `approval_required`, always sets `approved_at = NULL` (owner decision B-1: approval never carries over recipient drift), and increments `version` and `recipient_generation` while retaining subject, body, signature and edits. If approval is now required, it also sets `status = 'scheduled'`, releases the lease and records the approval-pending reason; the send stops for this run. If approval is not required, it leaves the row `sending` under the same lease and delivery continues under the new generation. Thus an approval-to-no-approval change clears the old approval but does not require a new one.

B4. **Failure.** A Liaison, contact, review-all or VIP read failure is a retryable failure for this run. The row is never sent to the stored Cc and its posture is never weakened because a read failed.

B5. **Rows with an activity but no send intent are not re-addressed.** The full exposure is a crash after activity-id persistence, a failure in the post-create source-eligibility read, or a failure persisting send intent. Each can leave `dynamics_email_id IS NOT NULL` and `send_requested_at IS NULL`; if the Liaison changes before retry, the saved activity still sends as created, possibly to the former Liaison. **Owner decision B-2 (S551): this outcome is accepted and nothing is built to re-address it.** The production zero-row measurement was point-in-time and does not remove this prospective window.
- Detection is still required: when delivery encounters this state, emit a structured operational warning and return a flag that the cron counts in its summary, without a Dataverse Liaison read or recipient mutation. A later repair would clear the saved activity id under a new generation; A5 makes that possible, but it is outside this plan.

This removes revision 0's interim stop, so its open requirement 1 no longer applies.

## Tests

- A1: send intent set and activity unaccepted → no second `sendEmail`, for cron and send-now, even when `last_error_code` is null or different; late acceptance on a later run → sent and finalized.
- A2: through the real `claimScheduledEmailSend`, a row with send intent and a null or existing unconfirmed code is claimed with `attempt_count` unchanged and the unconfirmed marker stamped/preserved; a row without send intent increments once. An unconfirmed row is under Needs attention, not upcoming; edit, approve and send-now are refused; Stop works; each display/guard reader goes through `isSendUnconfirmed`.
- A2 late acceptance: a stopped row with send intent that Dynamics accepts within 7 days → `sent`, finalized and in the FYI; after 7 days, or without send intent → untouched; the pass never calls `sendEmail`.
- A3: a transient stored-activity read error → retryable failure with no create or correlation lookup; 404 → `scheduled_email_activity_missing`, Needs attention and no later automatic claim; 403 → `scheduled_email_activity_forbidden` with the same manual-only behavior; 401 → transient. The due-query SQL and `scheduledEmailAttentionReason` agree on every code (parity test). No case creates or sends a replacement.
- A4: an edit or approval on a row with an activity → 409, row unchanged.
- A5: persist the exact post-crash row as `status = 'sending'`, both transport fields null, `lease_token = 'stale-token'`, an expired `locked_until`, version `v` and generation 0. A PD handoff with expected version `v` → `scheduled`, both lease fields null, version `v + 1`, generation 1 and unchanged `attempt_count`; the next claim creates generation 1 and never recovers the generation-0 draft. The same transition with a live lease or wrong version no-ops. A slow worker still holding the pre-reset `stale-token` after the reset cannot persist an activity id, record send intent or record failure, because each write is fenced on its lease token [VERIFIED via `scheduled-email-store.js:221-245,270-285`]. A generation-0 row created before the migration still recovers by today's key.
- A6: `cancelForSource` with a foreign lease → no-op.
- B: changed email with the same contact and the same normalized email with a different contact each trigger drift, generation increment and a rewritten ordered contact snapshot. An approved row that still needs approval → approval cleared and approval-pending with the reason. An approved row changing from approval-required to no-approval → `approval_required = false`, approval cleared, same lease retained and send continues. A Liaison read failure → no send; a new VIP contact → approval-pending; a concurrent lease turnover → the whole re-address/posture update no-ops.
- B5: seed an activity id with no send intent, then change the Liaison. Delivery emits the operational warning/summary flag, does not call re-address, leaves generation and saved activity recipients unchanged, and sends that saved activity as created. This regression pins owner decision B-2 rather than silently narrowing the accepted exposure.
- Crash-safety tests run against live Postgres (the `.pg.test.js` pattern in the CI ledger job), not mocked SQL.
