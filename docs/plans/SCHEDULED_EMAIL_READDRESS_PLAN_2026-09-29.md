## Why

The scheduled-email engine sends the grantee materials reminder (`grantee_abstract_reminder`, the only workflow the status table allows [VERIFIED via `lib/db/migrations/036_scheduled_email_messages.sql:56-57`, mirrored at `scripts/setup-database.js:891-892`; no later migration alters it]) for every program. It has hazards that do not depend on the Liaison change: it can send the same email twice once a send has been requested, it can adopt a stale draft, and it can drop a PD's edit (*Current engine facts*). Part A fixes these.

The Research Liaison switch gives **new** reminders the current Liaison. A row already queued keeps the recipients it was created with (liaison plan, owner answer 9). The point-in-time measurement found no queued rows, so the remaining prospective case is a Liaison change while a row waits to send. Part B covers it, reusing Part A's recipient generation.

## Part A: engine hardening (every program)

A1. **Send intent is the point of no return.** `send_requested_at IS NOT NULL` is the durable no-resend predicate; `last_error_code` is never used to decide whether transport may be called. Once send intent is set, the ordinary path reconciles only, as the test-Request path does today: accepted → record sent and finalize; otherwise → no `sendEmail`, and the row is marked unconfirmed (A2). This applies to send-now as well as the cron.

A2. **Unconfirmed is an error code, not a new status** (owner decision A-1, S551: error code; it needs no status CHECK migration). The row is set to `failed` with `last_error_code = 'scheduled_email_send_unconfirmed'`, and the lease is released.
- This happens **immediately**, in the `uncertain` branch that today skips `recordFailure` (`scheduled-email-service.js:384-392`), so the row does not sit in `sending` with a live lease, invisible to the digest query, until the next claim.
- One shared helper, `isSendUnconfirmed(row)`, is the only display/guard test for this state. Every reader of `failed` rows uses it (the digest grouping, the UI, the edit/approve/send-now guards and the due-send path), and each has a test. The transport guard remains the independent `send_requested_at` predicate, so a missing or temporarily cleared display marker cannot permit a resend.
- The separate reconciliation query in A7 keeps claiming it once per cron run, so a late acceptance is recorded and finalized without anyone acting.
- Keep `claimScheduledEmailSend` for ordinary delivery and add `send_requested_at IS NULL` to its fence. It continues to enforce schedule and approval unless `force = true`, and each successful ordinary claim increments `attempt_count`. A dedicated `claimScheduledEmailReconciliation` requires `send_requested_at IS NOT NULL`, status `scheduled`/`failed`/`sending` and no live lease; it ignores schedule and approval, preserves or re-stamps `scheduled_email_send_unconfirmed`, sets a lease and `updated_at`, and never changes `attempt_count`. Reconciliation reads the stored activity only: accepted → record sent and finalize; otherwise → release and retain the marker. It never calls `sendEmail`. The stopped-row pass takes no claim and never changes `attempt_count`.
- The digest lists it in a new **Needs attention** section, never under upcoming. Like approval-pending, the section repeats every day until the row is resolved, so no receipt or frozen membership is needed (this replaces revision 0's open requirement 3).
- The UI shows "Send status is uncertain. Check the email history before trying again" (`EMAIL_SEND_OUTCOME_COPY.uncertain`) and offers only Stop. Edit, approve and send-now are refused for these rows.
- **Late acceptance after a stop** (owner decision A-2, S551: check). Stop can end a row that Dynamics is still processing; so can the source-eligibility cancel at `scheduled-email-service.js:315`, which runs after the claim even when a send was requested. A daily cron pass reconciles every row with `status = 'stopped'`, `send_requested_at` set and `stopped_at` within the last 7 days, whoever stopped it. It reads the activity and never calls `sendEmail`. If Dynamics accepted it, a new store write moves the row from `stopped` to `sent`, fenced on those same columns (`recordScheduledEmailSent` needs a lease the stopped row does not have), and then finalizes it. The deliverable is marked Reminder sent, and the row appears in the PD's sent FYI. The rule: stopped wins unless Dynamics proves the email went. Every row with send intent has a `dynamics_email_id` [VERIFIED via `scheduled-email-store.js:234-245`]. Nothing here needs a migration.

A3. **A failed read of a stored activity is never absence by default.** When `dynamics_email_id` is set, a 401, 408, 429, 5xx or network error ends the attempt as a transient failure; if send intent exists, A2's unconfirmed marker is preserved. There is no correlation recovery and no create. Correlation recovery runs only when `dynamics_email_id` is null.
- Classification uses the HTTP status the read error carries (`error.status` [VERIFIED via `lib/utils/service-error.js:37-41`]); `getRecord` throws a structured error for every non-OK response [VERIFIED via `lib/services/dynamics/read-ops.js:133-136`]. A 404 is definitive missing. A 403 is transient: it may come from a service-principal role or policy that gets fixed, not from the row.
- A 404 stores `scheduled_email_activity_missing`; that row is excluded from automatic delivery and reconciliation and listed under **Needs attention** for manual recovery. A 403 stores `scheduled_email_activity_forbidden`, is also listed under **Needs attention** so the PD can see it, and stays in automatic retry; the next successful read clears the code. There is no counter.
- One shared helper, `scheduledEmailAttentionReason(row)`, returns `unconfirmed` (via `isSendUnconfirmed`), `activity_missing`, `activity_forbidden` or null, and every digest, UI and guard reader uses it. The ordinary query excludes both activity codes; the reconciliation-style query excludes missing but includes forbidden. SQL cannot call the helper, so parity tests pin those predicates to the helper.
- Manual recovery is explicit: staff check Dynamics and email history, send by hand if appropriate, then Stop the scheduled row. The engine does not clear the stored activity id, create a replacement, or retry a missing activity. Any manual source-record follow-up remains outside this automation.

A4. **No edits after the activity exists.** `updateScheduledEmailDraft` and `approveScheduledEmail` add `dynamics_email_id IS NULL AND send_requested_at IS NULL`. The UI disables editing on those rows and gives the reason. A PD who needs to change a row that is stuck after activity creation stops it and sends by hand.

A5. **Recipient generation for the PD-handoff rebuild.**
- The migration adds `recipient_generation INTEGER NOT NULL DEFAULT 0`, plus the migration-manifest entry, `scripts/setup-database.js` mirror and Atlas update. It is Part A's only new column.
- The correlation key is `wmkf-scheduled-recipient:<id>` at generation 0 (unchanged, so existing rows keep recovering) and `…:<id>:g<n>` after that. Every create and recovery uses the row's current generation, so an older generation's draft is never adopted.
- `reassignScheduledEmail` is one atomic reset. It accepts `scheduled` or `failed` rows and also `sending` rows whose lease is expired, but only when `dynamics_email_id IS NULL`, `send_requested_at IS NULL`, the PD differs, `version = expectedVersion`, and no lease is live. In the same update it writes the new PD/draft/posture, sets `status = 'scheduled'`, clears `lease_token` and `locked_until`, increments `recipient_generation` and `version`, and clears the former review/approval/error fields. `attempt_count` is retained as claim history. The next delivery must take a fresh claim.
- The cron passes the version of the row it just read; a wrong version or live lease is a no-op reported as deferred, as it is today.
- An older-generation draft left in Dynamics is an unsent draft. The cron summary counts rebuilt rows. A read-only probe that lists drafts by correlation key is the cleanup report; deleting drafts is a separate, owner-authorized step.

A6. **Fenced source cancel.** The two `cancelForSource` calls inside `deliverScheduledEmail` (`scheduled-email-service.js:315,363`) require the caller's `lease_token`. The pre-claim test-Request stop (`:305`) requires no live lease.

A7. **Reconciliation cannot starve ordinary sends.**
- `listDueScheduledEmails` adds `send_requested_at IS NULL` and excludes both `scheduled_email_activity_missing` and `scheduled_email_activity_forbidden`, so its 100 slots go only to ordinary rows that may still send. Neither send-intent reconciliation nor stored-activity 403 retries can fill it.
- The same reconciliation-style query takes at most 25 rows, status `scheduled`/`failed`/`sending`, no live lease and not `scheduled_email_activity_missing`, ordered by `updated_at ASC`. It selects either `send_requested_at IS NOT NULL` or a stored activity with `send_requested_at IS NULL` and `last_error_code = 'scheduled_email_activity_forbidden'`. The cron runs it once per run after ordinary delivery; the stopped-row seven-day pass stays separate.
- Send-intent candidates use `claimScheduledEmailReconciliation` from A2. Forbidden/no-intent candidates use a separate lease-fenced read claim requiring the stored activity id, null send intent and exact forbidden code. That path only reads the saved activity. Another 403 or transient read failure retains the code and releases the lease; 404 changes it to missing; a successful read clears the code, releases the lease and returns the row to ordinary eligibility for a later run. It never performs correlation recovery, creates an activity or calls `sendEmail`; the next ordinary run decides whether to record an already accepted activity or request its first send.
- Rotation uses existing `updated_at`, not a new schedule. Both dedicated claims set `updated_at = NOW()` when they acquire the lease, just as the current send claim does [VERIFIED via `lib/services/scheduled-email-store.js:199-206`]; their release/clear writes also set it. Therefore every successfully claimed candidate moves behind untouched candidates even when its read fails. A fence-losing row is not updated or rotated because it was not claimed; after the competing lease releases or expires, it remains eligible.
- Replace the global digest limit with `ROW_NUMBER() OVER (PARTITION BY pd_systemuser_id ORDER BY scheduled_send_at, created_at, id)`, retaining rows with rank `<= 100`. There is no global cap or rotation: every PD with eligible work is represented every day, with at most 100 rows. Also return the per-PD total and log/count a cap warning for each PD whose total exceeds 100; FYI receipts cover only selected ids.

## Part B: recipient and approval-posture reconciliation (after Part A)

B1. **Where.** In `deliverScheduledEmail`, after a successful ordinary claim and the source-eligibility check but before any activity lookup, inspect a transport-pristine row (`dynamics_email_id` and `send_requested_at` both null). Resolve the Liaison with `resolveRequestLiaison` plus a contact read, the same as row creation, and recompute review-all plus VIP posture. For this workflow, creation and re-address writes keep `recipient_contact_ids` in `[PI, Liaison?]` order so the stored Liaison contact id is an explicit part of the comparison.

B2. **Independent drift decisions.** Recipient drift means either the Liaison contact id changed or its trimmed, lowercased email changed, including a Liaison/Cc gained or dropped. The contact-id comparison is independent of the email comparison, so the same address on a different contact still drifts. Posture drift means the recomputed posture requires approval while the stored `approval_required` is false, even though PI and Liaison are unchanged: for example, review-all changed from false to true or an existing recipient became VIP-flagged.
- **Owner decision B-3 (S551): re-check at send time, tightening only.** This replaces the decide-once rule for rows not yet sent. Recipient and posture drift are evaluated independently; either may require a lease-fenced transition before any activity lookup. A tightening returns the row to approval-pending. A relaxation (review-all turned off or a VIP flag removed) changes nothing. The ordinary cron claim enforces schedule and approval unless forced [VERIFIED via `lib/services/scheduled-email-store.js:211-215`], while send-now passes `force: true` and bypasses those gates [VERIFIED via `pages/api/scheduled-emails/[id].js:82-88`]; Send-now is only available to the row's own PD (the route passes that PD's `systemuserid` [VERIFIED via `pages/api/scheduled-emails/[id].js:82-88`]), so on a forced claim the PD's action is the approval: posture-only tightening is skipped. Recipient drift on a forced claim still re-addresses and, under B-1, returns the row to approval-pending, so send-now answers "Recipients changed: the institution's Liaison changed. Review and send again" rather than sending to a Cc the PD has not seen. A posture-only transition increments `version` but not `recipient_generation`.
- The re-check adds a Dataverse read (review-all, `lib/services/email-automation-preferences.js`) and a Postgres read (VIP flags, `scheduled-email-store.js:526-534`) to each ordinary claim. Under B4 a failed read delays the send to the next run; it never sends on the stored posture.

B3. **One transition, then authoritative continuation.** The transition is fenced on lease token, expected version, `sending` status and both transport fields null. On recipient drift it persists the recomputed `approval_required` (either direction, since the recipients changed), writes Cc and the ordered recipient ids, clears `approved_at` (owner decision B-1), and increments `recipient_generation`. On posture-only tightening it atomically sets `approval_required = true` **and `approved_at = NULL`**, because an editable no-approval row may already carry an approval; it leaves recipients and generation unchanged. Every drift increments `version` while retaining subject, body, signature and edits. If approval is required, it sets `status = 'scheduled'`, releases the lease and records the approval-pending reason, and this run stops. Otherwise it remains `sending` under the same lease.
- The service must assign `message` to the transition's `RETURNING *` row before continuing. A null return means the lease/version fence was lost: abort this delivery with no activity lookup, create, recovery or send. The generation-specific correlation key, rendered recipients and activity create all use the returned row, never the pre-transition object.

B4. **Failure.** A Liaison, contact, review-all or VIP read failure is a retryable failure for this run. The row is never sent to the stored Cc and its posture is never weakened because a read failed.

B5. **Rows with an activity but no send intent are not re-addressed.** The full exposure is a crash after activity-id persistence, a failure in the post-create source-eligibility read, or a failure persisting send intent. Each can leave `dynamics_email_id IS NOT NULL` and `send_requested_at IS NULL`; if the Liaison changes before retry, the saved activity still sends as created, possibly to the former Liaison. **Owner decision B-2 (S551): this outcome is accepted and nothing is built to re-address it.** The production zero-row measurement was point-in-time and does not remove this prospective window.
- Detection is still required: when delivery encounters this state, emit a structured operational warning and return a flag that the cron counts in its summary, without a Dataverse Liaison read or recipient mutation. A later repair would clear the saved activity id under a new generation; A5 makes that possible, but it is outside this plan.

This removes revision 0's interim stop, so its open requirement 1 no longer applies.

## Tests

- A1: send intent set and activity unaccepted → no second `sendEmail`, for cron and send-now, even when `last_error_code` is null or different; late acceptance on a later run → sent and finalized.
- A2: the ordinary claim refuses a row with send intent. The dedicated reconciliation claim accepts it regardless of future `scheduled_send_at` or missing approval, leaves `attempt_count` unchanged and stamps/preserves the unconfirmed marker. Start with a future, unapproved row; send-now claims it through `force: true`, records send intent, and returns uncertain. A later cron reconciliation claims it despite both ordinary gates, reads the activity, never calls `sendEmail`, releases it unresolved with a newer `updated_at`, and the 25-row query rotates to older untouched candidates on the next run. An unconfirmed row is under Needs attention, not upcoming; edit, approve and send-now are refused; Stop works; each display/guard reader goes through `isSendUnconfirmed`.
- A2 late acceptance: a stopped row with send intent that Dynamics accepts within 7 days → `sent`, finalized and in the FYI; after 7 days, or without send intent → untouched; the pass never calls `sendEmail`.
- A3: a 401, 408, 429, 5xx or network stored-activity read error → transient failure with no create or correlation lookup; 404 → `scheduled_email_activity_missing`, Needs attention and no later automatic claim; 403 → `scheduled_email_activity_forbidden`, Needs attention and the shared read-only retry lane. - A4: an edit or approval on a row with an activity → 409, row unchanged.
- A5: persist the exact post-crash row as `status = 'sending'`, both transport fields null, `lease_token = 'stale-token'`, an expired `locked_until`, version `v` and generation 0. A PD handoff with expected version `v` → `scheduled`, both lease fields null, version `v + 1`, generation 1 and unchanged `attempt_count`; the next claim creates generation 1 and never recovers the generation-0 draft. The same transition with a live lease or wrong version no-ops. A slow worker still holding the pre-reset `stale-token` after the reset cannot persist an activity id, record send intent or record failure, because each write is fenced on its lease token [VERIFIED via `scheduled-email-store.js:221-245,270-285`]. A generation-0 row created before the migration still recovers by today's key.
- A6: `cancelForSource` with a foreign lease → no-op.
- A7 send-intent fairness: seed more than 100 unresolved rows with send intent and one ordinary due row; the ordinary query still returns and sends the ordinary row. The shared reconciliation query returns at most 25 rows ordered by oldest `updated_at`; successful claims bump `updated_at`, and successive runs reach every untouched row before recycling a still-unresolved one.
- A7 forbidden fairness: seed more than 100 older rows with a stored activity, null send intent and `scheduled_email_activity_forbidden`, plus one ordinary due row. Across runs the ordinary row sends, each retry batch is at most 25, repeated 403s move claimed rows to the tail, and all forbidden rows are eventually read. A successful activity read only clears the code/lease; it neither creates nor sends, and the row becomes ordinary-eligible next run.
- A7 digest fairness: seed more than 500 eligible rows across multiple PDs, including at least one PD with over 100. Every PD is represented, no PD contributes more than 100, the overflowing PD produces its own cap warning, and selected FYI ids alone are receipted.
- B recipient drift: changed email with the same contact and the same normalized email with a different contact each trigger drift, generation increment and a rewritten ordered contact snapshot. An approved row that still needs approval → approval cleared and approval-pending with the reason. An approved row changing from approval-required to no-approval → `approval_required = false`, approval cleared, same lease retained and send continues. A Liaison read failure → no send; a new VIP contact → approval-pending; a concurrent lease turnover → the whole re-address/posture update no-ops.
- Send-now under B: a forced claim with posture-only tightening sends; a forced claim with recipient drift re-addresses, returns approval-pending and does not send.
- B posture drift (owner decision B-3): start with unchanged PI/Liaison, `approval_required = false` and non-null `approved_at` (allowed by the current approval write). Review-all false→true and an existing recipient becoming VIP each atomically persist `approval_required = true`, set `approved_at = NULL`, release the lease and perform no activity lookup. A posture-only transition does not increment generation. With unchanged recipients, turning review-all off on an approved row changes nothing and it sends as approved; a Dataverse review-all read failure → no send this run.
- B3 returned-state continuation: recipient drift with no approval required returns generation `g + 1` and rewritten Cc; replace `message`, then assert the created Dynamics activity uses correlation key `…:g<g + 1>` and the returned Cc. A null transition return aborts before activity lookup or create.
- B5: seed an activity id with no send intent, then change the Liaison. Delivery emits the operational warning/summary flag, does not call re-address, leaves generation and saved activity recipients unchanged, and sends that saved activity as created.
