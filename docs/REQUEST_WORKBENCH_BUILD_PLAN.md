PDs need to start finding reviewers for the going-forward set **before** the formal status flip. Today the only blocker is that `pages/api/reviewer-finder/my-proposals.js` surfaces only `akoya_requeststatus eq 'Phase II Pending'` requests — the going-forward requests aren't in that state yet, and advancing the status early fires a live PowerAutomate trigger (intake recompute).

Justin handed over the going-forward set (35 `akoya_requestnum` values, two ascending batches of 18+17 — see Appendix A). Direction (confirmed this session): **build the full Request Workbench now**, introduce the new `reviewers` grant **additively** (retire old keys later), commit the 35 numbers as a **trivially-editable throwaway** config (complete but may change), and **modernize the Find experience** rather than port the stale UI verbatim.

The Workbench is the locked redesign destination (`docs/REQUEST_WORKBENCH_SCOPING.md`, `[[project-reviewer-apps-redesign-direction]]`): tier-2 cycle dashboard → tier-3 per-request Workbench, with the Reviewers tab consolidating today's Reviewer Finder (Find) + Review Manager (Invite/Track/Completed). **Multi-session build**; phases ordered by deadline value.

### Find modernizations + applicant-reviewer model (this session)

1. **Find defaults to the request's documents.** The Workbench Find panel auto-loads the proposal via `load-proposal` (requestId→SharePoint→Blob); the PDF-upload entry is **dropped** from the Workbench Find tab (kept only on the standalone Reviewer Finder, which we are not deleting yet).
2. **Applicant-recommended + applicant-excluded reviewers unify on `wmkf_appreviewersuggestion`** (the per-(person, request) engagement junction — where Reviewer Finder candidates already live, keyed to the request). A **new single picklist field** `wmkf_applicantdisposition` with values **`recommended` / `excluded`** (null = staff/Claude-discovered, the normal case) distinguishes them. Origin still rides on the existing free-text `wmkf_sources` (`applicant` added).
   - **Per-request scoping is by construction:** the disposition lives **only on the junction row**, never on the global `wmkf_potentialreviewer` person record. A person excluded by one applicant stays fully eligible/enrichable for every other request. Dedup/resolve an excluded name to an existing person row is fine, but write **nothing global** marking them as a reviewer-to-avoid.
3. **Equal-footing enrichment for recommendations, on the PD's search run.** Applicant recommendations are seeded as candidates and run through the **same** `discover` (PubMed verify → publications, institution/coauthor COI) + `enrich-contacts` (email/ORCID/website) pipeline as Claude candidates, as part of the Find action the PD already triggers (not auto-on-load). Excluded entries are only lightly resolved/matched (enough to recognize the person), not bibliometrically enriched.
4. **Exclusions: keep free-text raw + mirror.** `wmkf_excludedreviewers` (free-form, deployed) stays the human-readable source for the applicant's *reasons*; its parsed names are **mirrored** into structured `disposition=excluded` junction rows that drive the search filter. The Find search applies the excluded set **scoped to the current request only**, pre-fills the existing `excludedNames` soft-block, and flags any returned candidate matching as a conflict.
5. **One-time legacy migration this cycle.** Legacy GOapply writes applicant suggestions to `akoya_request.wmkf_potentialreviewer1..5` lookup slots (user-attested: still in use this cycle; **no live code reads them** per `docs/AUDIT_S154_MEMORY.md:83`). Ingestion reads those slots + the free-text excludes and **idempotently materializes** the junction rows (recommended/excluded). The new intake portal writes these junction rows directly going forward, deprecating the slots + free-text (see `[[project-intake-portal-reviewer-capture]]`).
6. **Reviewer-decision content comes from `wmkf_abstract`, not an extracted PDF page.** The legacy `summaryPages`→`extractPages`→`summaryBlobUrl`→`wmkf_summarybloburl` flow is **removed entirely**. The modern reviewer surface already renders `wmkf_abstract` (verified below), so the abstract is the decision content. **Removal blast radius (all touch points):** strip page-extraction from `analyze.js`; stop persisting `summaryBlobUrl` in `save-candidates.js`; drop it from `my-candidates.js` output + `pages/reviewer-finder.js` display; the invitation no longer attaches it (legacy `.eml` path retired). Because `analyze.js` is **shared**, this also removes the summary attachment from the still-live standalone Reviewer Finder — acceptable, since the summary-attachment mechanism is being retired wholesale. `wmkf_summarybloburl` + the Dataverse `wmkf_summarypages` cycle field become dead — **unread by the Workbench's new code paths** (no schema deletion), **except `maintenance-service.js` L317 continues reading `wmkf_summarybloburl` for historical orphan-blob cleanup** (see §Phase 3).

(One-time legacy migration, run lazily per request when a PD opens Find; optional batch backfill over the 35 pre-populates dashboard counts.) Rules hardened after Codex round 1:

    - **No-email recommendation** (slot person with no email, and enrichment can't find one): still ingested as a `recommended` candidate, **flagged "no email — not invitable until contact found."** Enrichment (`enrich-contacts`) attempts to resolve one; if none, behavior is identical to any existing Reviewer Finder candidate lacking an email (`send-emails` already skips no-email recipients — `send-emails.js:230`).
  - **Excluded** (from free-text `wmkf_excludedreviewers`): create a structured `disposition=excluded` row **only on a confident person match**. *Confident match (Round-2 fix — define explicitly):* (1) **exact email** match, OR (2) **normalized-name + affiliation** above a similarity threshold, reusing the existing dedup/normalization primitive (`DeduplicationService` name-normalization). **Ambiguous (multiple candidates) or low-confidence → do NOT create a structured row and do NOT create a new person row**; fall back to the **free-text → `excludedNames` soft-block** (the existing path) + surface the unresolved name to staff. So exclusion always works (soft-block) even when no confident person row exists, and the global person registry is never polluted with junk.
  - **Race-safe upsert (not find-then-create):** the junction has the `(wmkf_potentialreviewer, wmkf_request)` alternate key (`wmkf_app_reviewer_suggestion.json:214-219`) — use an **atomic alternate-key upsert** (or catch the 412/duplicate and re-fetch). `DynamicsService.createRecord` throws on conflict and does not handle the race today; lazy-on-Find-open ingestion can run concurrently for the same request.
  - **Recommended + excluded collision** (same person in both, contradictory but possible — alternate key allows only one row): **excluded wins** (honor the applicant's "don't use") and the row is flagged for staff visibility. **Closed in Phase 0 (S208, post-review):**

**Phase 3 acceptance criteria (enforce when ingestion first writes excluded rows):**
