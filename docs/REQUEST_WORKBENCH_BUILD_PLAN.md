## Context

D26 Phase II peer review has a real deadline (Phase I→II flip ~mid-June 2026, with BILL honoraria attached). PDs need to start finding reviewers for the going-forward set **before** the formal status flip. Today the only blocker is that `pages/api/reviewer-finder/my-proposals.js` surfaces only `akoya_requeststatus eq 'Phase II Pending'` requests — the going-forward requests aren't in that state yet, and advancing the status early fires a live PowerAutomate trigger (intake recompute).

Justin handed over the going-forward set (35 `akoya_requestnum` values, two ascending batches of 18+17 — see Appendix A). Direction (confirmed this session): **build the full Request Workbench now**, introduce the new `reviewers` grant **additively** (retire old keys later), commit the 35 numbers as a **trivially-editable throwaway** config (complete but may change), and **modernize the Find experience** rather than port the stale UI verbatim.

The Workbench is the locked redesign destination (`docs/REQUEST_WORKBENCH_SCOPING.md`, `[[project-reviewer-apps-redesign-direction]]`): tier-2 cycle dashboard → tier-3 per-request Workbench, with the Reviewers tab consolidating today's Reviewer Finder (Find) + Review Manager (Invite/Track/Completed). **Multi-session build**; phases ordered by deadline value.

### Find modernizations + applicant-reviewer model (this session)

1. **Find defaults to the request's documents.** The Workbench Find panel auto-loads the proposal via `load-proposal` (requestId→SharePoint→Blob); the PDF-upload entry is **dropped** from the Workbench Find tab (kept only on the standalone Reviewer Finder, which we are not deleting yet).
2. **Applicant-recommended + applicant-excluded reviewers unify on `wmkf_appreviewersuggestion`** (the per-(person, request) engagement junction — where Reviewer Finder candidates already live, keyed to the request). A **new single picklist field** `wmkf_applicantdisposition` with values **`recommended` / `excluded`** (null = staff/Claude-discovered, the normal case) distinguishes them. Origin still rides on the existing free-text `wmkf_sources` (`applicant` added).
   - **Per-request scoping is by construction:** the disposition lives **only on the junction row**, never on the global `wmkf_potentialreviewer` person record. A person excluded by one applicant stays fully eligible/enrichable for every other request. Dedup/resolve an excluded name to an existing person row is fine, but write **nothing global** marking them as a reviewer-to-avoid.
3. **Equal-footing enrichment for recommendations.** Applicant recommendations are run through the **same** verify (PubMed → publications, institution/coauthor COI) + enrich (email/ORCID/Scholar + h-index/citations) pipeline as Claude candidates. **SHIPPED S211** via `POST /api/workbench/enrich-recommended` (SSE) behind an explicit **"Enrich recommended reviewers"** button in the Find tab (the user chose explicit-click over auto-on-load). The endpoint loads the request's `disposition=recommended` rows, resolves `proposalInfo` (reusing the client `analysisResult` or one `analyzeProposal` call on the loaded `blobUrl`; fail-loud if neither), verifies the names (carrying `potentialReviewerId`/`suggestionId` through `verifyClaudeSuggestions`'s `...suggestion` spread), COI-checks them, enriches with `persist:false`, then writes back per-person bibliometrics onto `wmkf_potentialreviewer` (race-safe `upsertByPotentialReviewer`; S213: the `researcher` adapter targets the person, the `wmkf_appresearcher` sidecar is dropped) and persists deterministic COI tags to the junction `wmkf_matchreason` (atomic `setMatchReason`, ETag/If-Match, fail-closed on excluded). Enriched recommendees render in the Find tab badged **"Applicant recommended."** Excluded entries are still only soft-block names (option B), not enriched. COI is computed on the full set (verified + unverified) and the coauthor check folds in `coInvestigators` (not just the PI). **Parity gap (pre-existing):** the shared `discover.js` search path checks coauthorship against `proposalInfo.proposalAuthors` only, which `parseAnalysisResponse` normalizes to the PI alone (`reviewer-finder.js:243`) — so the main reviewer search does NOT flag co-investigator coauthorship. enrich-recommended is intentionally more complete here; folding co-Is into `discover.js` (+ the standalone) is a separate, unstarted follow-up.
4. **Exclusions: keep free-text raw + mirror.** `wmkf_excludedreviewers` (free-form, deployed) stays the human-readable source for the applicant's *reasons*; its parsed names are **mirrored** into structured `disposition=excluded` junction rows that drive the search filter. The Find search applies the excluded set **scoped to the current request only**, pre-fills the existing `excludedNames` soft-block, and flags any returned candidate matching as a conflict.
5. **One-time legacy migration this cycle.** Legacy GOapply writes applicant suggestions to `akoya_request.wmkf_potentialreviewer1..5` lookup slots (user-attested: still in use this cycle; **no live code reads them** per `docs/AUDIT_S154_MEMORY.md:83`). Ingestion reads those slots + the free-text excludes and **idempotently materializes** the junction rows (recommended/excluded). The new intake portal writes these junction rows directly going forward, deprecating the slots + free-text (see `[[project-intake-portal-reviewer-capture]]`).
6. **Reviewer-decision content comes from `wmkf_abstract`, not an extracted PDF page.** The legacy `summaryPages`→`extractPages`→`summaryBlobUrl`→`wmkf_summarybloburl` flow is **removed entirely**. The modern reviewer surface already renders `wmkf_abstract` (verified below), so the abstract is the decision content. **Removal blast radius (all touch points):** strip page-extraction from `analyze.js`; stop persisting `summaryBlobUrl` in `save-candidates.js`; drop it from `my-candidates.js` output + `pages/reviewer-finder.js` display; the invitation no longer attaches it (legacy `.eml` path retired). Because `analyze.js` is **shared**, this also removes the summary attachment from the still-live standalone Reviewer Finder — acceptable, since the summary-attachment mechanism is being retired wholesale. `wmkf_summarybloburl` + the Dataverse `wmkf_summarypages` cycle field become dead — **unread by the Workbench's new code paths** (no schema deletion), **except `maintenance-service.js` L317 continues reading `wmkf_summarybloburl` for historical orphan-blob cleanup** (see §Phase 3).

## Excluded-row fail-closed boundary (Codex S208 review)

Codex reviewed the Phase 0 diff and flagged that the excluded-row guard, while correct where applied, isn't enforced at every write/token sink. Phase 0 creates **zero** excluded rows (ingestion is Phase 3) and the primary defense — excluded rows are `selected=false` and filtered out of every candidate/invite/count list — already prevents them from surfacing in any action UI. Still, the boundary was tightened and the remainder is recorded as Phase 3 acceptance criteria.

**Closed in Phase 0 (S208, post-review):**
- `verifySuggestionToken` rejects an excluded row even with a previously-minted live token (the single chokepoint for all external context/respond/upload; reported as `revoked`).
- `updateLifecycle` reads + rejects an excluded row on **every** lifecycle write (not just complete transitions) — one extra read per write, accepted deliberately so all callers fail closed without per-route checks.
- `findById` throws on excluded; `ensureToken` + `regenerate-token` refuse to mint.

**Phase 3 acceptance criteria (enforce when ingestion first writes excluded rows):**
- **Token revocation on exclusion:** when ingestion materializes/flips an existing token-holding engagement to `excluded`, revoke its external token (don't rely solely on the verify-time guard). The "excluded wins" collision rule is the natural home.
- `mintAndStore` (the exported mint sink) should itself fail closed, not only its current callers.
- Staff post-acceptance direct writes (`mark-received-no-file`, `lib/services/review-upload.js`) bypass the adapter — route them through it or add an inline disposition reject. (Unreachable while excluded rows never reach acceptance, but close the gap when ingestion lands.)
- `generate-emails` legacy `.eml` mark-as-sent loop writes by id directly — moot once the legacy path is retired (Find-mod 6), otherwise add the reject.
