# Manual presentation video pairs

[VERIFIED via branch source and isolated media/database tests, 2026-10-23; not deployed] Migration 089 introduces `manual_presentation_video_pairs` and adds nullable `manual_pairing_id` to `presentation_video_splits`. Each split must have exactly one source: the existing copied Zoom row or a manual pair. The production migration tracker remains through 085; 086–089 have not been applied there. Fresh installs replay the same migration manifest.

Admission requires both existing video-split access and separate `MEETING_MANUAL_VIDEO_PAIRING_ACCESS` (`off` by default, `on` or exact `test:<request GUID>`), current Meeting Tracker staff identity and the authoritative active request/visit binding. An uploaded-audio transcript must retain its normalized original source ID, SHA-256, bytes and duration. A plain text transcript cannot prove correspondence. Current RECORDING winner and Graph size/quickXorHash establish MP4 identity. Staff cannot supply file paths, hashes, provenance or a claimed verification receipt.

The existing video-split route has strict `manual-status`, `manual-upload` and `manual-start` commands. Mint reserves an actor-owned random pathname under `manual-video-pairs/`, then returns a fifteen-minute exact-path, no-overwrite, declared-size/type-limited private Blob capability. Only original MP3/M4A up to 200 MiB is admitted; bytes never pass through a Function request body. Finalize freshly authorizes and checks current source identities plus persisted pathname, owner, 24-hour stage expiry, Blob size/type; completion may finalize after the fifteen-minute capability expires. A ready upload can resume without another upload. Two uncleaned stages per request bound retained private input.

The same locked split-start transaction consumes the ready stage and queues work. Manual replacement must name the exact current review split (or explicit null); drift refuses before consuming the stage or superseding review. Approved editions remain active. Existing processing or registering work retains its fence. No provider call, video processing or Board publication happens in this staff request.

The existing video worker owns asynchronous processing and its lease/Sandbox cleanup. Before naming or creating a paid Sandbox, it reads bounded original bytes server-side and verifies original SHA/size with time reserved for creation, transfer and install. It then writes only those bytes into the non-persistent media Sandbox with a bounded transfer signal. No broad Blob credential enters it. Version 3 of the existing pinned FFmpeg recipe requires exactly one audio track and zero timeline, then compares exact decoded mono 16 kHz signed 16-bit PCM hash and sample count for original audio and MP4. It rejects changed/re-encoded or offset media rather than inferring alignment. Existing CFR, frame/sample boundary, cut-content and discussion-tail checks remain. A successful cut persists content-free PCM proof under the current cutting lease before output upload. A verified pair is reusable for later boundary corrections only while original audio and MP4 identities still match. It is not a Board approval.

States: `awaiting_audio` → `ready` → `attached` → `verified`; definite correspondence failures become `rejected`. Ordinary failed or superseded cuts atomically restore an unexpired attached stage to `ready` for explicit retry without another upload. Processing state/failure and retry live on the existing split; the pair stores input identity, private staging path and content-free proof. Failed manual work requires corrected source/original upload; the preparation video step reuses a matching successful split without regenerating summaries. Human ending review and assigned Coordinator edition approval remain required.

The existing video drain and daily maintenance each clean at most two eligible stages per pass, even with admission off. Verified/rejected raw input becomes eligible after capability expiry; other staging expires after 24 hours. Cleanup locks the exact stage, excludes active attached processing, deletes only its stored pathname and clears it after successful deletion. Failures retain it with fifteen-minute backoff so one failing path does not starve unrelated cleanup. Verified proof metadata remains; unused cleaned unverified rows without split references expire after thirty more days. Cleanup skips only a missing table before migration. Existing Sandbox cleanup stays independent of processing state.

Tests use actual migrations in random loopback PostgreSQL schemas and tiny local synthetic FFmpeg media; route/worker/UI tests replace all external transport. No paid Sandbox, real staff media, production migration or deployment was used. The conservative exact-audio requirement is a supported limitation, not a claim that arbitrary converted files can synchronize.

Metadata eTag distinction: worker/pair reuse checks content size/quickXorHash and tolerates metadata-only eTag drift. Existing candidate approval remains stricter: changing the saved RECORDING row eTag requires a fresh cut/review. This increment does not weaken that existing approval contract.
