# Durable meeting material preparation

[VERIFIED via source and isolated PostgreSQL tests, 2026-10-23] Branch-built continuation of the Meeting Coordination plan. Migration 087 is allocated after the owner-authorized filenames-only tracker read and inspection of 355 local/remote refs. It is not applied to Production. Apply 086 then 087 and verify physical tables, columns, constraints and indexes before runtime deployment. No live processing acceptance or paid application call is asserted.

`meeting_material_preparations` identifies one request/active-visit/input fingerprint, frozen content-free source and recording/slides references, initiating profile/system user, published source identity and monotonic version. The request foreign key requires sticky presentation-approval enrollment. Creation and all five child rows commit together; a repeated input uses `ON CONFLICT DO NOTHING` without restamping.

`meeting_material_preparation_steps` holds `source`, `transcripts`, `presentation_summary`, `discussion_summary`, `video`; states are `pending`, `running`, `succeeded`, `blocked`, `unknown`. Each step has an opaque attempt ID, bounded claim count, optimistic version, 330-second lease, bounded reference-only options/output and sanitized failure code. Dependency checks require source completion before transcripts and transcript completion before summaries/video. A partial unique index enforces one running step per preparation. Claim holds the parent lock and rechecks running siblings in a fresh statement. Every finish requires the exact unexpired lease token. Polling an existing video does not consume its retry budget; each attempt has a 24-hour waiting limit and then requires explicit resume, reusing the matching child. Waiting for the source publication’s live recovery lease likewise does not exhaust attempts.

Entry: `PreparationPanel` → `/api/meeting-tracker/visits/[requestId]/preparation` → `preparation-service.js`/`preparation-store.js`. POST persists before returning, never runs a model. Source publication is a durable child operation referencing the existing saved correction receipt and expected version; a completed or uncertain publication is read/reconciled by exact operation instead of blindly repeated. Already-published confirmed sources are also supported. The currently connected UI prepares an already saved review; the single combined save/review interaction remains subsequent UI work.

Execution: `/api/cron/drain-meeting-material-preparations`, once a minute in source, one child per invocation, maxDuration 300. `MEETING_MATERIAL_PREPARATION_ACCESS` defaults off; accepted values are `on` or `test:<request GUID>`, with test claims scoped in SQL. Existing transcription/readiness and child-video controls still apply. The worker rechecks active profile, mapped Dynamics identity, current Meeting Tracker grant (or existing superuser access), request/visit binding, enrollment and frozen recording/slides/source identity. Explicit retries may record a new execution actor without rewriting the initiating actor. Source publication, transcript generation and video cutting reuse existing services/receipts. Preparation never changes Board visibility.

## Summary uncertainty and acknowledgement compatibility

Migration 087 adds summary `preparation_id`, `generation_outcome`, `initiated_by_profile_id`, `initiated_at` and makes the three acknowledgement columns nullable as an all-null-or-all-present tuple. Existing historical true acknowledgements remain. New Meeting Tracker calls without acknowledgement record initiation separately. The shared reservation uses the existing request/kind advisory lock and checks **all** `reserved`, `dispatched`, `unknown` ownership rows before the ordinary active/age/expiry selection, including legacy callers. Owned reservation and dispatch require the exact live parent step attempt.

Unknown submission is never automatically retried. Expired worker leases retain the uncertainty tombstone; active draft reads show protected ownership even beyond fourteen days, and maintenance does not expire it. A known completed result is recovered without another call after parent worker death; expired, discarded or superseded text becomes visible actionable work. A reserved undispatched child is conditionally retired and safely resumed without an uncertainty warning. A genuinely old legacy generation or interrupted publishing claim is preserved, not automatically replaced by preparation. Explicit abandonment requires coordinator authorization, expected step version and possible-duplicate-charge acknowledgement; it retires the old child and changes the attempt ID. Completion of an unknown or abandoned old attempt cannot restore it. Existing edited ready drafts block with exact ID/version; replacement must name that version. Generated text retains its existing fourteen-day policy. Uncertainty tombstones and metadata remain independently retained.

The Meeting Tracker audio/Zoom provider checkbox is removed across strict routes, import callers and meeting-only runtime queuing. `transcription_jobs.initiated_by_profile_id`/`initiated_at` record the queue initiator; any historical `non_sensitive_acknowledged_at` is preserved with `COALESCE`. The separate admin pilot's acknowledgement check and queue path are unchanged.

## Limits and retention

No automatic parent/step cleanup in this increment: one bounded row per deliberate input identity, five bounded child rows; retry updates the same step and preserves successful siblings. No transcript text, speaker names, credentials, tokens or media URLs are stored in the new ledgers. Source/file/lease checks use snapshot semantics across Postgres/Dataverse/SharePoint, not a cross-system transaction. Migration-first deployment, disabled-by-default admission and the edition-aware rollback floor are release prerequisites. The combined save/review interaction, coordinator collection dispatch, consultant pickers, keyboard agenda ordering and writeup-first Workbench are now branch-built continuations; see the implementation plan and continuation review receipt. Manual video-source pairing remains separate implementation work. Presentation invitation email uses its own migration-088 ledger, not this preparation queue.
