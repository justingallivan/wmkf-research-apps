## Producer and persistence

`lib/services/retraction-refresh-service.js` downloads the official Crossref GitLab CSV, validates every row, and bulk-loads TEMP `retraction_refresh_stage` inside one advisory-locked transaction. The stage has no durable rows and is dropped by commit/rollback. Keyed merge preserves existing `retractions.id`; source removals are counted and refused when any foreign key references the corpus. More than a 10% row-count drop requires operator review. No screening history or staff decisions are rewritten.

The transaction publishes corpus changes and `retraction_dataset` together: singleton key 1, monotonic generation, SHA-256 of the actual downloaded bytes, fixed source URL, optional source revision, effective row count, upstream source_row_count, retained_records provenance manifest, format version, publication time and last successful full-source check time. Repeated identical bytes with an identical retention manifest do not republish or change generation/publication time; only last_checked_at advances. A→B→A increments generation each changed publication. No metadata row is invented for legacy corpus data. Two owner-approved, source-controlled backup snapshots (13045/67801), with author indexes re-derived by the current normalizer, are staged only while their IDs are absent upstream. The manifest carries notice URL, review date, reason, backup SHA and payload SHA; raw CSV checksum remains unchanged. If an ID returns upstream, its current source row wins and retained provenance clears. A manifest change increments publication generation, including with unchanged CSV bytes.

Migration 092 widens `retractions.publisher` and `subject` to TEXT. The official CSV inspected on 2026-11-02 has maximum lengths 500 and 263 respectively, exceeding the old VARCHAR(255) declarations. Other constrained columns fit that source sample; the service checks actual target widths before COPY and never truncates fields.

`maintenance_runs` records each attempt and safe counts/checksum/header diagnostics. Metadata is authoritative even if post-commit audit logging fails; the response marks auditRecorded=false and an existing system alert is attempted. A lost COMMIT acknowledgement is publication-uncertain, never a claim that the old corpus was preserved. Resource cleanup cannot turn a known committed publication into a failed import.

## Consumers

`lib/services/retraction-dataset.js` reads the publication before and after all people’s corpus queries in `IntegrityService.screenApplicants`. Stable managed generations are saved in each person's `sources.retraction_watch.dataset`; a changed/unverifiable generation clears provisional corpus matches and marks every person's corpus source incomplete before saving or emitting final results. There is no transaction across paid provider calls. The final whole-run event is authoritative for the standalone UI/export and Workbench persistence.

Absent schema or an unpublished singleton is explicit unrecorded provenance, not fabricated metadata. Existing runs keep unknown provenance. A metadata-query failure is unverified and blocks a new approval through explicit source errors and the current-policy dataset validation predicate. The final fence also attaches retained-record provenance to matching rows. UI/history/PDF/Markdown/JSON expose the recorded generation/upstream checksum and any retained-record label, as well as publication/check dates; a 45-day freshness warning is based on the last successful full-source check, not the last changed publication. Staleness alone adds no funding/progression/approval gate.

Production manual worker is enabled with the existing bearer secret; it remains disabled by default elsewhere. **Monthly activation is owner-approved and source-configured, pending production verification:** `0 6 1 * *`, the 1st at 06:00 UTC.
