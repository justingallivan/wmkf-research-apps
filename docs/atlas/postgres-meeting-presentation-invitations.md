# Research-presentation invitation receipts

[VERIFIED via source and isolated local PostgreSQL, 2026-10-23] `meeting_presentation_invitations` is the separate request/visit-scoped email ledger introduced by migration 088. Migration 088 is applied to Production and the runtime is deployed (2026-10-24 canonical-runner and schema readback). After all release checks passed, owner-authorized ordinary activation set `MEETING_PRESENTATION_INVITATION_ACCESS=on` on 2026-10-24; see the [controlled production release](../audits/MEETING_CONTROLLED_DEPLOYMENT_2026-10-24.md). It does not create calendar events, use the session agenda ledger, or request applicant uploads. `MEETING_PRESENTATION_INVITATION_ACCESS` defaults off and accepts `on` or `test:<request-guid>`; apply and verify migration 088 before enabling it.

The Meeting Tracker invitation route checks app access and DAL context; service checks require a current eligible linked staff profile, the session mailbox and an accessible eligible request. Preview resolves the saved visit's required To and optional Cc groups from the existing recipient directory, without filling empty groups. The frozen snapshot includes request/visit identity and ETag, attendee refs and mailboxes, sender identity/signature and reviewed subject/message. Preview creates a frozen Postgres row only. Sending verifies the full context before creation and again before dispatch, with lease and impersonation checks at each intervening boundary, requires the original sender and exact operation version, and requires `DYNAMICS_IMPERSONATION_ENABLED=true` and uses explicit actor plus `noFallback:true` for Dynamics create and SendEmail.

A server-generated operation ID, versioned five-minute leases, persisted `creating`/`send_requested` intent and a unique unresolved-operation index prevent duplicate dispatch under retries or concurrent previews. States are `prepared`, `creating`, `activity_created`, `send_requested`, `unknown`, `sent`, `failed`. Any currently authorized staff member may reconcile by reading the exact activity or correlation key; reconciliation never submits transport or changes the original sender provenance. Dynamics statuses 3/6/7 establish accepted transport, not inbox delivery. An uncertain send that still reads Draft remains unresolved; an unambiguously recovered creation-only draft or absent creation-only activity can be retired without sending (the versioned lease prevents a late creator from advancing). Unknown ownership survives preview and content expiry. A separate `email_hash` verifies the exact Dynamics subject, HTML body, sender and normalized To/Cc envelope before SendEmail; `email_verified_at` persists that check before dispatch intent. Later acceptance requires the same activity/correlation and `envelope_hash`, while allowing Dynamics to normalize the sent subject/HTML. These proofs survive text redaction. Reads hide expired message content immediately even if bounded physical cleanup has not reached the row.

Previews expire after fifteen minutes. Existing daily maintenance runs independently of admission, including when the access flag is off (an unapplied table is safely skipped). It processes at most 100 deletions and 100 redactions per run: expired fifteen-minute previews and thirty-day resolved records are deleted; thirty-day unresolved snapshot/message/recipient content is redacted while retaining the operation, actor/request/visit identity, activity/correlation identity, state and uniqueness fence. Admission serializes per normalized request UUID and caps retained rows at 100 per request. Expired or deleted previews never create or send an activity.

Producers: `lib/services/meeting-coordination/invitation-service.js` and `invitation-store.js`; maintenance calls `cleanupInvitations`. Consumers: strict `/api/meeting-tracker/visits/[requestId]/invitation` and PresentationInvitationPanel in the before-meeting workspace. No raw media, provider credentials or tokens are stored.

Tests apply the actual SQL in a random loopback PostgreSQL schema: concurrent claim, lease expiry/token mismatch, unresolved uniqueness, recipient shape, content redaction, scoped cleanup and concurrent cap enforcement including differently cased UUIDs. Service/route/UI tests replace all remote transport and identity seams. The isolated tests send no real email or production write; subsequent deployment is recorded above. No real email rehearsal was performed.

Operational recovery: use the retained activity ID to inspect the exact email in Dynamics. If an uncertain Send still shows Draft, the original sender or administrator must confirm it is unsent and cancel it using the existing Dynamics controls, then choose **Check email status**. A closed/cancelled activity resolves without dispatch. For mismatched or duplicate correlation activities, an administrator inspects the exact activities and closes the unsent drafts; reconciliation remains read-only. Never clear the ledger fence in SQL or use another preview to bypass uncertain transport. A missing activity after durable Send intent remains unknown and requires transport investigation; absence alone cannot prove non-delivery.
