## Safety contract

The managed service validates complete CSV/header/IDs/dates/widths before publishing. It stages and merges under a transaction-scoped advisory lock, preserving the live table/IDs and atomically recording checksum/generation. Failed work before COMMIT leaves the corpus unchanged. Lost COMMIT acknowledgement is explicitly uncertain: inspect authoritative metadata before retrying. Audit logging failure after a confirmed commit is reported separately and does not mean the corpus stayed unchanged.

If unchanged bytes and the same retention manifest produce different derived rows, `retraction_derived_corpus_differs` reports diff counts and refuses publication; Dry-run reports `sourceUnchanged: true` and the same row differences; do not approve publication when that combination has nonzero differences without a reviewed explanation. A changed retained manifest, whether from reviewed snapshot/provenance edits or changed author-index derivation, is explicit `retentionChanged: true` and intentionally creates a new generation. That path republishes the full staged corpus and does not apply the same-manifest drift refusal; inspect all dry-run differences. Investigate both unmanaged writers and normalization-code changes, then obtain a separately reviewed re-derivation plan. Unchanged upstream bytes with the same retained manifest only advance last_checked_at, not publication time/generation. A row-count drop beyond 10% or a removal with foreign-key references is refused. Do not work around those guards: inspect a dry-run manifest and revise the exact operation with owner approval. Old manual imports cannot run after the metadata schema exists, and all old/external writers must be quiet before initial cutover.

The fixed retention policy contains only reviewed records 13045 and 67801, from the verified backup: thirteen bibliographic fields stay frozen, while authors_normalized is re-derived with the current normalizer and included in the retained payload hash. It inserts either row only when that ID is absent upstream; a returning upstream ID wins. Source checksum and sourceCount describe the downloaded CSV, while count includes retained rows. The manifest and per-match labels expose the legacy provenance and notice verification, rather than claiming those rows occur in the current feed. Any change to these source-controlled snapshots/provenance requires review; do not add a generic no-delete mode or edit CSV bytes. Reappearance under a different record ID requires a human policy review.

## Isolated rehearsal

Use `scripts/rehearse-retraction-refresh.cjs` with an explicitly configured `RETRACTION_REHEARSAL_URL` for a temporary loopback database. It does not load `.env.local` or fall back to application credentials. Apply the normal existing-DB migrations to that scratch database first. The command defaults to dry-run; `--file=/absolute/source.csv` selects a local test/downloaded CSV, and `--publish` permits publication **only in that selected loopback database**. Neither argument is accepted from HTTP callers. Temporary prepared files are cleaned up; keep the safe JSON summary/checksum for review, not a tracked copy of the large CSV.

## Screening provenance

New screens record publication generation/checksum and dates with each person's Retraction Watch source. If the corpus changes mid-run, final results are incomplete and cannot receive a new staff approval. No automatic paid retry occurs. Existing runs show that the dataset version was not recorded; their saved evidence and reviews are not rewritten. Any production recovery from the scoped backup requires separate authorization and must restore corpus/publication metadata coherently under the writer lock, preserving monotonic generation and making unverifiable provenance fail closed. Do not replay the raw dump into a running app or erase publication history. No automated production restore was added.

A freshness warning appears after 45 days without a successful full-source check; it does not revoke an approval or determine misconduct.
