## Recall Rule

Read this before any reviewer-finder design that ranks candidate SOURCES,
proposes pool/roster reuse, elevates applicant-suggested reviewers, or plans
"reviewer network" features.

## The facts (owner-stated, Justin, 2026-07-08; nuanced same day)

1. **Applicant-suggested reviewers: ~1 per panel — a VERY RECENT, reactive
   policy decision**, made because a colleague would stack panels with
   applicant-suggested people ("not a great outcome"). High quality (80% blind
   PD pick-rate in the S246 origination experiment) but policy-limited for now;
   as a recent reactive rule it could evolve — do not hard-code it. The
   friends-of-PI *bias* was already recorded
   (`docs/REVIEWER_FINDER_RETRIEVAL_REDESIGN_PLAN.md` Part C §8); the
   operational cap was not, until now.
2. **Reviewer reuse is per-PD practice, not an org constant.** Justin has not
   re-used a reviewer in ~4 years (one data point; reasons: sparse data —
   improving with current legibility work; welcome-preservation; field breadth).
   A former colleague DID reuse reviewers repeatedly, but has departed. So
   `docs/STRATEGY.md:81` ("good reviewers get called upon repeatedly") reflects
   the departed colleague's real practice — stale as a description of current
   staff, not false. No doc fix required; don't cite it as current practice.
3. **Referral capture is a MULTIPLIER on the engine, not an independent
   channel.** A declining expert can only suggest alternates if the engine
   found and contacted them in the first place — tier-1 discovery quality
   compounds through the referral chain. Combined with 1–2: the
   Claude-assisted origination engine is the product (fills nearly every panel
   seat under current practice); applicant recommendations are worth more as
   community *search seeds* than as candidates.

**Why:** the 2026-07-08 holistic review
(`docs/audits/reviewer-holistic-review-fable-2026-07-08.md`) initially
recommended a roster flywheel and applicant-recs-first slate from the repo
record alone; the owner corrected and then nuanced it same-day. These practice
facts are not derivable from code or docs — and they are *practice/policy*, not
structure: re-check with the owner before treating them as invariants.

**How to apply:** score finding investments by (a) per-proposal engine quality
(referral value compounds on it), (b) referral capture, (c)
applicant-recs-as-seeds. Deprioritize — don't permanently rule out — pool-reuse
and per-person reviewer-history features; they become viable only if staff
practice changes. Related:
